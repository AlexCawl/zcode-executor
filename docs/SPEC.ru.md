## Проблема

Пользователь продумал задачу разработки в Claude Code и хочет, чтобы код изменил локальный ZCode (GLM), оставив себе только планирование и приёмку.
Сейчас такого канала нет: приходится либо вручную вставлять задание в ZCode App, либо поручать изменения самому Claude. В первом случае нужно переключаться между приложениями, не остаётся записей,
а запросы разрешения исполнителя приходится отслеживать; во втором квота Claude расходуется на работу, которую можно передать другому исполнителю.

## Решение

Плагин Claude Code `zcode-executor`. Claude записывает договорённости в файл задания и одной командой CLI создаёт сессию, отправляет задание и ждёт результата.
Исполнитель изменяет код в изолированном рабочем дереве. Когда он запрашивает разрешение, сначала применяются жёсткие правила, затем запрос проверяет недорогая модель; если решение не получено, запрос переходит в ожидание ответа,
пока Claude не передаст его человеку. После завершения хода Claude выполняет приёмку по `git diff` и тестам. Для каждой сессии выделен отдельный каталог, все события сохраняются на диск.

## Решения по реализации

### Слои и технологический стек

- Четыре слоя: протокол (запуск app-server, сопоставление JSON-RPC запросов и ответов, маршрутизация и устранение повторов обратных запросов, жизненный цикл сессии, определение завершения хода),
  рабочий процесс (реестр, список разрешённых каталогов, распределение уровней моделей, runner, очередь и блокировка, сохранение на диск), шлюз согласования (жёсткие правила, проверка моделью, ожидание ответа),
  оболочка (CLI, skill, шаблон файла задания).
- Node ≥ 22, ESM, только `.mjs`, без зависимостей времени выполнения и сборки. Типы из TypeScript-прототипа слоя согласования удаляются вручную.
  Код, перенесённый из zcode-acp, сохраняет уведомление Apache-2.0; в корень репозитория добавляется `NOTICE`.
- Прямое соединение с `zcode app-server --stdio`, без промежуточного ACP. В конвертах нет поля `jsonrpc`.
- При запуске дочернего процесса устанавливается `NO_COLOR=1`, а `ZCODE_MODEL` удаляется из окружения. По умолчанию zcode ищется в каталоге ресурсов ZCode App.

### Протокольный слой

- Один клиентский объект управляет одним дочерним процессом: отправка запроса возвращает Promise с сопоставлением по id; полученное сообщение с `method` и `id` считается обратным запросом
  и передаётся зарегистрированному обработчику. Обратные запросы с одинаковым `requestId` повторяются каждую секунду; обрабатывается только первый, на повторы отправляется тот же ответ (пока ответа нет, сохраняются id конвертов, после получения результата ответ отправляется каждому).
  Запросы без `requestId` (на реальной установке встречался только `session/requestRuntimePreferences`) распознаются по «методу + полным параметрам»: полностью одинаковые параметры означают повтор одного запроса; разные параметры проходят обработчики отдельно.
  Кеш ответов сохраняется только до границы хода (готовые ответы очищаются перед следующим `session/send`): если другая сторона повторно использует `requestId`, ответ предыдущего хода не применяется.
- При запуске дочернего процесса переменные окружения наследуются, кроме собственных учётных данных агента-хозяина (фиксированный список `HOST_CREDENTIAL_ENV` в `lib/appserver.mjs`, включая `GITHUB_TOKEN` / `GH_TOKEN`),
  независимо от того, поступили они из окружения текущего процесса или из переданного вызывающим кодом `env`. Список разрешённых переменных не используется (`HOME` и `PATH` обязательны; отсутствие любой из них ломает работу). Имена исключённых переменных выводятся одной строкой в stderr, без значений.
- Перед созданием сессии выбирается провайдер и записывается персональный файл конфигурации провайдера. Источников два: Coding Plan аккаунта (платформенный ключ, расшифрованный из `~/.zcode/v2/credentials.json`, и список моделей встроенного файла провайдеров, D19)
  и `provider` из `~/.zcode/v2/config.json`. Один вариант выбирается по уровню модели и приоритету провайдера, затем преобразуется в персональный файл конфигурации провайдера (decisions D14; формат см. в
  разделе «Изменения 3.12.2» файла `docs/reference/zcode-app-server-protocol.md`); путь передаётся дочернему процессу через переменную окружения `ZCODE_PERSONAL_PROVIDER_CONFIG_FILE`.
  Без неё create отклоняется. (До 3.12 читались все включённые провайдеры, варианты с пустыми models или
  `enabled:false` отбрасывались, а сформированная полная таблица `registry` передавалась дочернему процессу через `workspace/updateProviderRegistry`. С 3.12 этот способ
  не работает; см. decisions D10.)
- Рукопожатие: на `session/requestRuntimePreferences` отвечать `{nativeSearchEnhancementsEnabled:false, memoryEnabled:false, askUserQuestionAutoResolutionEnabled:false}`. Отсутствие ответа приводит к зависанию create.
- Параметры `session/create`: оба поля `workspace:{workspacePath, workspaceKey}` заполняются cwd, `mode:"build"`, `persistence:"immediate"`,
  `titleGenerationEnabled:false`, **обязательное поле `model`** (с 3.12 заменяет `runtimeModel`, decisions D14; старый формат см. в
  разделе «Первая реальная отправка» файла verified.md), необязательные `thoughtLevel` и `toolDenylist`. В resume поле `model` не передаётся.
- События сессии поступают через `session/subscribe` и без изменений добавляются в файл событий. Границы хода — от первого `turn.started` после отправки до `turn.completed` или `turn.failed`;
  ход с `turn.started.payload.inputSource`, равным `background_task`, запускается самим фоновым инструментом и целиком игнорируется (раздел «Background Tasks» документации протокола). В первой версии нет резервного определения завершения при отсутствии сигналов.
- Вмешательства сообщением используют `sendText` через `v4/command` (`requestedDelivery:"guide"`, действует на следующей границе инструмента; при отсутствии границы ставится в очередь после завершения хода). ACK, отличный от accepted/noop/duplicate, или delivery, равный startNow (ход уже закончился), явно записывается как ошибка.
- Завершение: `session/close`, затем EOF в stdin.
- Список моделей и распределение по уровням вычисляются локально из `~/.zcode/v2/config.json` (до 3.12 отдельно вызывался `workspace/readState`,
  теперь этот метод удалён; см. decisions D14). При рукопожатии `doctor` сопоставляет модели из раздела `zcode-executor` в `settings.model.available`,
  возвращённом `session/create`, с локальным списком и предупреждает об отсутствующих. Другие команды рукопожатия не выполняют.
- Параметры `workspace/generateText`: `{workspace, selection:{providerId, modelId, options:{reasoningLevel}}, prompt или messages, querySource, maxOutputTokens, operationId}`
  (до 3.12 параметр назывался `modelRef`, а уровень размышления передавался через `modelRef.variant`; формат см. в decisions D14). В `querySource` передаётся
  `zcode-executor.review` (проверено на реальной установке, verified.md).

### Слой рабочего процесса

- Каталог данных — `~/.zcode-executor/`, переопределяется переменной окружения `ZCODE_EXECUTOR_HOME`.
- Ключ Jev хранится в `review.jev.apiKey` конфигурации плагина; runner читает его через `loadConfig` при каждом запуске соединения независимо от наследования переменных окружения.
- Поля конфигурации (все необязательные):

  ```json
  {
    "allowedRoots": ["~/.zcode-executor/worktrees"],
    "waitTimeoutSec": 3600,
    "preferredProvider": "builtin:bigmodel-coding-plan",
    "tiers": { "fast": "GLM-5.3-Flash", "strong": "GLM-5.3" },
    "review": {
      "enabled": true,
      "model": "GLM-5.3-Flash",
      "thought": "low",
      "timeoutMs": 60000,
      "fastMaxTokens": 300,
      "slowMaxTokens": 2000,
      "jev": { "apiKey": "jev_…" }
    },
    "environment": ["…给模型审批看的本机环境说明…"],
    "sensitive": ["…敏感位置…"]
  }
  ```

  Сохранённые строки примера означают «описание локального окружения для проверки моделью» (`environment`) и «чувствительные места» (`sensitive`).

- В реестре одна запись на сессию, ключ — локальный id (`x_` + 8 шестнадцатеричных цифр): `id`, `sessionId` (идентификатор zcode, появляется только после первого хода), `title`, `cwd`, `isWorktree`, `repoRoot` (корень исходного репозитория, если cwd — рабочее дерево, иначе null; отсюда шлюз согласования читает документы проекта), `tier`, `provider`, `modelId`, `thoughtLevel`, `toolDenylist`, `createdAt`, `lastOutcome`.
  `list` показывает только записи реестра, выводя оба id. `new` не создаёт сессию zcode (decisions D13).
- Два уровня моделей: `fast` / `strong`. Автоматическое распределение: если id или метка модели содержит `flash`, `lite`, `mini`, `air` (без учёта регистра), она относится к `fast`,
  остальные — к `strong`. Если на уровне несколько моделей, выбирается наибольшая версия; варианты с `disabledReason` пропускаются; настройка `tiers` переопределяет автоматический результат.
  Если одна модель есть у нескольких провайдеров, **приоритет у провайдера coding plan**: сначала используется настроенный `preferredProvider`;
  если он не задан, выбор среди включённых провайдеров идёт по суффиксу id: `-coding-plan` раньше `-start-plan`, остальные в конце. Для внутреннего китайского сервиса используются `builtin:bigmodel-*`,
  для международного — `builtin:zai-*`; выбирается включённый. Если включены оба, берётся первый по порядку config.json (до 3.12 — по порядку
  `workspace/readState`, теперь этот метод удалён; см. decisions D14).
  Даже без `--tier` провайдер выбирается по этому правилу, а не напрямую из `settings.model.current`, возвращённого `session/create` (на реальной установке там был `builtin:bigmodel` с оплатой по API Key).
- Уровень размышления по умолчанию — `high`. Перед созданием сессии значение проверяется по `reasoning.levels` модели; явно указанное пользователем значение, отсутствующее в списке, даёт код завершения 2.
  С 3.12.2 при создании сессии всегда передаётся `reasoningLevel` (обязателен для create серии GLM 5.3): значение реестра → `reasoning.defaultLevel` модели →
  `'high'` (`reasoningLevelFor` в `lib/tiers.mjs`). На проверку моделью это не влияет: если модель не поддерживает уровень, он по-прежнему не передаётся.
- Список разрешённых каталогов: cwd после преобразования в абсолютный путь должен находиться под одним из `allowedRoots` (при сравнении префикса добавляется разделитель). Иначе код завершения 2.
  Если cwd не является рабочим деревом (`git rev-parse --git-dir` и `--git-common-dir` совпадают), выводится только предупреждение в stderr.
- При запуске runner сначала вызывает `session/resume`; если в реестре нет sessionId или resume сообщает Session not found, вызывается `session/create` (`model`, thoughtLevel и toolDenylist берутся из реестра; до 3.12 здесь передавался `runtimeModel`, см. decisions D14), затем sessionId записывается обратно (при пересоздании добавляется событие `executor.recreated`).
- Runner: один процесс на сессию, без демона, **всегда в фоне** (detached, журнал в `runs/<id>/runner.log`). В ожидании ответа runner должен сохранять соединение без ответа,
  а завершение процесса переднего плана с кодом 5 не должно разрывать его. `send` только ставит отправку в очередь и запускает runner, если живого ещё нет; `--wait` лишь отслеживает файлы. Ответы на запросы разрешения и вопросы передаются runner через `runs/<id>/answer.json`.
  Жизненный цикл: получить блокировку O_EXCL (если блокировка есть, прочитать pid; живой процесс — отказ, мёртвый — замена) → только после получения блокировки очистить старые pending / answer и маркеры stop / cancel, созданные до запуска текущего runner (более новые адресованы ему, терять их нельзя)
  (runner, не получивший блокировку, не должен трогать файлы работающего runner) → запустить дочерний процесс → `session/resume` (если sessionId отсутствует или resume сообщает
  Session not found, выполнить create) → `session/subscribe` → циклически брать самую раннюю запись очереди (сортировка по временной метке имени файла, удаление только после обработки) →
  при пустой очереди или маркере stop закрыть дочерний процесс и завершиться.
- Содержимое `runs/<本地 id>/` (`本地 id` означает «локальный id»): `state.json` (phase: running / idle / pending / exited / stale; pid принадлежит самому runner),
  `events.jsonl`, `last.json` (outcome, reason, время начала и конца предыдущего хода), `pending.json`, `answer.json` (ответ, удаляется runner после обработки), `queue/`, `tasks/`, `lock`, `stop`, `cancel`, `runner.log`.
  Для `runs/` и вложенных каталогов используются права 0700, для файлов — 0600 (`ensureRunsDir` ужесточает их при каждой отправке, исправляя оставшиеся от старых версий 0755). Корень каталога данных не меняется. Временные имена файлов для атомарной записи содержат случайную часть, создание исключительное (`wx`).
- Снимки задания: при постановке `send --task` в очередь содержимое файла сохраняется как `runs/<id>/tasks/<sha256>.md`; запись очереди и событие `executor.send` содержат `taskSha256`.
  Проверка моделью читает намерение только из снимка по `taskSha256` с проверкой хеша. Если поля нет, снимок отсутствует или содержимое не соответствует хешу, эта часть файла задания не включается в намерение (недостаток оснований может лишь чаще передавать запрос человеку); исходный файл по пути `task` повторно не читается.
  Если `--task` указывает не на обычный файл, код завершения 1; отправка не ставится в очередь, внепиковый талон не получается.
- Для уведомлений `session/event` в файл событий записываются полные params (с `type`, `seq`, `payload`); остальные уведомления (`computer-use/operation-event`, `process/mcpTelemetry` и т. п.) записываются как `{"method", "params"}`.
  Формат собственных событий проекта — `{"type":"executor.<动作>", "at":<ISO 时间>, ...}` (`动作` означает «действие», `ISO 时间` — «время ISO»).
  Действия: `send` (текст сообщения, путь task, `taskSha256` при наличии файла задания), `steer`, `result` (подведение итога каждого хода), `recreated` (пересоздание потерянной на стороне zcode сессии), `gate` (stage: hard / no-allow-option / review-fast / review-slow / review-failed / review-disabled / gate-error / question; decision: allow|ask; ruleId, reason; review-fast также может содержать reviewer / reviewModel / reviewSchema / probabilities / usage / durationMs),
  `approve`, `deny`, `answer`, `cancel`.
- Итог определяется по `turn.completed.payload.resultType` (2026-09-21 проверено по исходникам ZCode: результат, отличный от success, тоже приходит через `turn.completed`):
  отсутствие значения или `success` → outcome `done`; `cancelled` → `cancelled`; `error_*` → `failed` (reason содержит значение resultType);
  `turn.failed` → `failed`; завершение по cancel → `cancelled`; истечение `--wait` → отправить `session/stop` (запрос с id),
  outcome `timeout` (после срабатывания stop ожидается завершение хода с resultType:"cancelled", но наружу по-прежнему сообщается timeout:
  код 3 означает «отправить снова и продолжить», а 4 — ошибку хода); ожидание ответа → `blocked`.
- Коды завершения: done 0; ошибка использования или запуска 1; отказ 2; timeout 3; failed / cancelled 4; blocked 5.
- `--wait` по умолчанию использует `waitTimeoutSec` конфигурации, `--timeout` переопределяет его. При ожидании ответа код 5 возвращается немедленно, без ожидания тайм-аута.
- `follow` читает только mtime файла `last.json` и конец `events.jsonl`, не подключаясь к протоколу. `status` читает только файлы.
- `cancel`: записать оба маркера stop и cancel; если есть ожидающий запрос, сначала ответить отказом. Увидев cancel, runner отправляет `session/stop`, после 5 секунд ожидания принудительно отключается и очищает очередь.
- `--stream` выводит текст `model.streaming` и сводки `tool.updated` в stderr.

### Шлюз согласования

- Обратные запросы `interaction/requestPermission` поступают в шлюз согласования; `interaction/requestUserInput` сразу переходит в ожидание ответа на вопрос.
- Порядок трёх этапов фиксирован: жёсткие правила → проверка моделью → ожидание ответа. Для каждого запроса разрешения записывается одно итоговое событие `executor.gate`; сведения о предварительной проверке Jev помещаются в его `preScreen`. Исторический смысл `fastReview` сохраняется, чтобы не нарушить существующие подсчёты.
- Таблица жёстких правил зафиксирована в коде. Она использует категории режима auto Claude Code и дополняется двумя механическими правилами проекта (`checkHardRules` в `lib/review/hard.mjs`; совпадение сразу переводит запрос в ожидание ответа):
  - Выход за пределы рабочего дерева (`outside-worktree`): если аргументы инструмента содержат файловый путь (ключи `file_path` / `notebook_path` / `path`) и он находится за пределами cwd → ожидание ответа.
    Путь разрешается так же, как ядром: от корня по сегментам, символические ссылки раскрываются на месте (включая последний сегмент; оборванная ссылка считается по расположению её цели), `..` поднимается к уже разрешённому реальному родительскому каталогу;
    несуществующие сегменты добавляются как есть (создание файлов — обычная операция). `fs.realpathSync` не используется: он сначала выполняет лексическую нормализацию и сворачивает `<cwd>/link/../x` в выглядящий внутренним `<cwd>/x`.
    Отдельно разрешаются исходная строка и результат `path.normalize`; если хотя бы один путь снаружи, правило срабатывает. Ошибки разрешения (ELOOP, ENOTDIR, EACCES и т. п.) означают невозможность оценки и тоже активируют правило.
    Инструменты записи (Write, Edit, MultiEdit, NotebookEdit, ApplyPatch) без пригодного для проверки ключа пути также активируют правило. Для Bash это жёсткое правило выхода за пределы не применяется.
  - Самозащита (`self-modify-approval`): контуром управления считаются пути под `config.home` (каталогом данных), кроме `worktrees/` и cwd текущей сессии. Аргумент пути внутри контура управления активирует правило
    (до него дело доходит только при конфигурации, в которой рабочее дерево содержит каталог данных; обычно раньше срабатывает правило выхода за пределы). Также активируют правило буквальные ссылки на контур управления в исходном `command` (Bash) или `code` (инструменты js)
    (сначала раскрываются `~`, `$HOME`, `$PWD`, `$ZCODE_EXECUTOR_HOME`, относительные пути разрешаются от cwd), а также вхождение `zcode-executor <子命令>` (`子命令` означает «подкоманда»). Проверки находятся в `lib/review/self-guard.mjs`;
    тесты обеспечивают соответствие таблицы подкоманд `COMMANDS` оболочки. Распознаются только прямые записи; границы описаны в decisions D23.
- Исходная проверка моделью ZCode по-прежнему состоит из быстрой и углублённой проверок; перед ними можно добавить предварительную проверку Jev. Любой результат Jev, кроме pass, продолжает исходную цепочку; только flag исходной быстрой проверки запускает углублённую, которая разбирает allow / deny / ask (deny преобразуется в ask).
  Вывод быстрой проверки распознаёт только отдельные Y / N (также yes / no, без соседних букв и цифр). Успехом считается появление только Y во всём тексте; отсутствие обоих или наличие одновременно Y и N означает flag и переход к углублённой проверке.
  Реализация быстрой проверки выбирается автоматически по тому, является ли `review.jev.apiKey` непустой непробельной строкой: с ключом используется Jev; без ключа — существующая модель уровня fast и `review.thought` (по умолчанию `low`). Отдельные shadow/off/screen или перечисление `provider` не вводятся, второй ключ из переменных окружения не читается.
  Углублённая проверка всегда использует существующий `workspace/generateText`; **первая строка вывода содержит заключение** (`结论: allow` / `结论: ask` / `结论: deny <规则 id>`, где `结论` означает «заключение», а `规则 id` — «id правила»), далее идёт причина.
  Сначала разбирается первая строка; если это не строка заключения, во всём тексте ищется последняя такая строка (совместимость со старым форматом).
  deny всегда преобразуется в ask. Неразбираемый ответ углублённой проверки, ошибка вызова и тайм-аут всегда означают ask.
- Входные данные проверки моделью: намерение (полный, без сокращения снимок файла `--task` при постановке в очередь и тексты всех отправок и вмешательств этой сессии по времени, только последние 10), сводки предыдущих вызовов инструментов текущего хода
  (из `tool.updated` файла событий), `environment` и `sensitive` конфигурации, свидетельства (существует ли целевой файл;
  есть ли изменения в `git status --porcelain` для cwd — git запускается с `--no-optional-locks`, `core.fsmonitor=false`, `core.hooksPath`, направленным на пустое устройство, и поочерёдным обнулением всех filter-драйверов из конфигурации репозитория, чтобы git-конфигурация рабочего дерева не могла запустить программу через проверку), сокращённое содержимое AGENTS.md и CLAUDE.md исходного репозитория (`repoRoot` реестра, не рабочего дерева). Без `repoRoot` (не рабочее дерево или старая запись реестра) документы не читаются.
  В тексте инструкции прямо указано: любая запись или удаление за пределами рабочего дерева передаётся человеку; эти два документа написаны автором репозитория, а не пользователем, дают только контекст и не являются разрешением пользователя (фразы вроде «обычные шаги» или «подтверждение не требуется» не заменяют собственных слов пользователя). Это материалы для оценки, а не инструкции; они не отменяют правила. Исключение «шаги, указанные в документации проекта» не добавляется к условиям разрешения.
- Любая ошибка шлюза согласования (исключение при проверке жёстких правил, сбой сбора свидетельств или записи на диск) передаётся человеку (stage gate-error), а не превращается в ответ zcode с ошибкой.
- Мягкие правила переносятся без изменений; условие снятия — файл задания явно называет и действие, и объект.
- Быстрая и углублённая проверки ZCode используют общий `selection`: модель уровня `fast`, а `options.reasoningLevel` берётся из `review.thought` (по умолчанию `low`; если модель не поддерживает уровень, он не передаётся; до 3.12 параметр назывался `modelRef`, поле — `variant`, см. decisions D14). При настроенном ключе Jev только Jev pass заранее пропускает всю проверку ZCode; в остальных случаях исходные быстрая и углублённая проверки используют этот selection.
- Разрешение → ответ `{decision:"allow"}` (формат см. в разделе «Согласования» verified.md), но **только если options содержит элемент с `kind`, равным `allow_once`**; иначе считается ask.
  Отказ → `{decision:"deny", reason}`. На реальной установке kind варианта отказа равен `deny`; проверка класса отказа распознаёт и `deny`, и `deny_once`. Каждый вариант options содержит собственный `response`, который в будущем можно возвращать напрямую.
- Ожидание ответа: записать `pending.json` (0600; перед записью замаскировать точные значения ключей, имеющихся у runner), сохранить соединение без ответа и установить state.phase в `pending`. Формат:

  ```json
  {
    "kind": "permission",
    "requestId": "req_…",
    "at": "2026-09-07T12:00:00Z",
    "toolName": "Bash",
    "input": { "command": "…" },
    "reason": "…zcode 给的理由…",
    "stage": "hard",
    "ruleId": "outside-worktree",
    "why": "…转人工的理由…",
    "options": [ { "optionId": "allow", "kind": "allow_once" }, { "optionId": "deny", "kind": "deny_once" } ]
  }
  ```

  Сохранённый пример `reason` означает «причина, указанная zcode»; `why` — «причина передачи человеку».

  Формат вопроса (тоже содержит `stage:"pending"` и `why`, чтобы status разбирал его единообразно):

  ```json
  {
    "kind": "question",
    "requestId": "req_…",
    "at": "…",
    "stage": "pending",
    "why": "等人",
    "questions": [ { "question": "…", "multiSelect": false, "options": [ { "label": "…", "value": "…" } ] } ]
  }
  ```

  Сохранённое значение `等人` означает «ждём человека».

- `approve` отвечает `{decision:"allow"}` (требует allow_once в options); `deny` отвечает `{decision:"deny", reason}`, а на вопрос — `{action:"decline", reason:"人工拒答"}` (`人工拒答` означает «человек отказался отвечать»).
  `answer` отвечает `{action:"accept", content:{answers}}`. CLI и runner обмениваются через `answer.json`: `{requestId, decision}` / `{requestId, values}` / `{requestId, decline:true}`; requestId должен совпадать с текущим ожидающим запросом.
  С `--json` все три команды выводят `{id (локальный), sessionId (zcode, может быть null), requestId, kind (имя команды), pendingKind (permission|question), applied, eventType (тип события-квитанции runner, null, если не найдено)}`.
  applied определяется тем, изменился или исчез requestId ожидающего запроса. Когда runner отказывается отвечать вместо человека (cancel), он тоже записывает `executor.deny`; если approve пересекается с cancel, eventType достоверно сообщает deny.
  После ответа удаляется `pending.json`, записывается соответствующее событие, runner продолжает ждать завершения хода.
- В одной сессии одновременно может быть не более одного ожидающего запроса. Если runner отсутствует (pid мёртв), `approve` / `deny` / `answer` завершаются с кодом 2 и объяснением.
- Ожидание ответа не истекает.

### Необязательная быстрая проверка Jev

- Условие включения только одно: `review.jev.apiKey` в `~/.zcode-executor/config.json` — непустая непробельная строка (проверяется, что она не состоит из пробелов, но при передаче Authorization исходное значение сохраняется; ключ самовольно не изменяется). Отсутствующее поле или полностью пробельная строка означают отсутствие настройки. Переменные окружения не являются источником ключа Jev, чтобы избежать разницы в приоритетах источников и наследовании окружения отсоединённым runner.
- `review.jev.proxy` (необязательно, D24): непустой адрес прокси `http://` или `https://` (может содержать userinfo, используется Basic Proxy-Authorization). При настройке HTTPS-запросы Jev проходят через CONNECT-туннель прокси (`lib/review/proxy-fetch.mjs`, собственная реализация без зависимостей; прокси из переменных окружения не используется — он разбирается только при запуске процесса, наследование окружения отсоединённым runner ненадёжно, а переменные попадут и в дочерний app-server). Условие включения не меняется: без `apiKey` Jev не включён, прокси не используется, `loadConfig` выдаёт предупреждение. Прокси socks не поддерживается. В `loadConfig` проверяется только формат адреса, не доступность; недоступный прокси обрабатывается как сетевая ошибка через существующие повторы и резервный путь.
- `review.jev.model` (необязательно, D25): непустая строка, ID или псевдоним модели Jev; по умолчанию `jev-latest`. Без `apiKey` действует то же предупреждение, что для proxy: Jev не включён, настройка не используется.
- При наличии ключа Jev работает как необязательная предварительная проверка и не заменяет исходную быструю проверку ZCode fast + low. Jev pass даёт раннее разрешение; остальные результаты поступают исходной быстрой проверке, затем при неуспехе — углублённой. Нет shadow и параллельной гонки. Без ключа исходная цепочка полностью сохраняется.
- Если `config.json` содержит ключ Jev, это должен быть обычный файл с правами не шире `0600` (владельцу чтение и запись, группе и остальным — ничего). При избыточных правах, символической ссылке или владельце, отличном от текущего uid, `loadConfig` отказывает в запуске с кодом 1 и сообщает только путь и способ исправления, не показывая ключ. Реализация не должна полагаться на подверженную гонке проверку «сначала lstat, затем read по пути»: после обнаружения ключа файл нужно заново открыть с `O_NOFOLLOW`, проверить через `fstat` того же fd и прочитать достоверное содержимое. Для прежних конфигураций без ключа Jev новые ограничения прав не добавляются. В документации и примерах записи конфигурации всегда требуется `chmod 600`; если в будущем появится команда записи конфигурации, она должна записывать атомарно и явно устанавливать `0600`.
- Порядок: жёсткие правила → проверка `allow_once` → необязательная предварительная проверка Jev → исходная быстрая проверка ZCode → при необходимости углублённая проверка → ожидание ответа. Jev flag/error/skip и исключения адаптера всегда направляются исходной быстрой проверке; она получает исходные action/context без подсказок вероятностями Jev. Ошибка её вызова по-прежнему даёт review-failed/ask; только неуспешный результат запускает углублённую проверку, её выходы сохраняются.
- Если локально известно, что необходимых свидетельств недостаточно, Jev пропускается без HTTP: опущен текст Write/Edit/MultiEdit, сокращена команда или сохранённое содержимое задания/сообщения, нет действительного намерения, невозможно надёжное маскирование. Пропуск использует decision:flag, outcome:skip, конечное перечисление metadata.reasonCode и attempts:0; это не оценка риска моделью. Нельзя безусловно пропускать проверку лишь из-за сложности команды.
- HTTP-адаптер использует встроенные в Node 22 `fetch` / `AbortController`, без зависимостей времени выполнения. Всегда вызывается `POST https://api.typesafe.ai/v1/systemone` с Bearer-ключом; модель задаётся `review.jev.model`, стандартный псевдоним — `jev-latest` (D25; порог 0.20 и схема `approval-v2` определены для `jev-1.13.0`, смена модели — на свой риск). Проверяется `model` ответа: при закреплённой версии требуется точное совпадение; для псевдонима допускается его повторение или номер версии, полученный при разрешении псевдонима, всё остальное — недопустимый ответ. Детерминированные 4xx вроде 401/422 не повторяются; для 408/429/529/5xx и ошибок соединения используются ограниченные повторы. Единый общий срок, по умолчанию 10 секунд, охватывает все fetch, чтение тела, Retry-After и backoff со случайной добавкой. Перед успешным возвратом срок проверяется повторно, ожидания не могут выйти за бюджет. Тело неуспешного ответа нужно очищать в ограниченных пределах. requestId ограничивается по длине, проверяется и маскируется.
- Схема верхнего уровня состояния Jev строго состоит из `intent` и `action`: `intent.taskContract` (последний файл задания, не более 8000 символов; при превышении сохраняются первые 6000 + последние 2000 с явным маркером сокращения), `intent.recentMessages` (последние 10 сообщений send/steer, не более 600 символов каждое), `action.tool`, `action.arguments`. Команда Bash после маскирования ограничена 4000 символами, при превышении так же сохраняются первые 3000 + последние 1000; значения путей нормализуются в `<WORKTREE>` / `<HOME>` / `<OUTSIDE_TMP>`. Текст Write/Edit/MultiEdit и старые/новые строки заменяются на `{omitted:true, chars, lines}`, содержимое не отправляется. В объектах/массивах на любой глубине значения ключей, совпадающих с apiKey/token/secret/password/Authorization без учёта регистра, заменяются на `<redacted>`; известные секретные значения также заменяются внутри строк. На верхнем уровне не отправляются projectDoc, environment, sensitive, проверки свидетельств, priorActions, полные события, переменные окружения и посторонний исходный код. Контрактные тесты проверяют сокращение и пропуск как положительными, так и отрицательными утверждениями.
- Вопросы Jev зафиксированы как пять полей Noul в схеме `approval-v2` (v1 — исторический альтернативный путь): `scope_conflict`, `outside_worktree_write`, `credential_or_exfiltration`, `destructive_or_external`, `unrelated_or_gratuitous`. Сложный Bash, конвейеры, дочерние оболочки, фильтрация вывода, пакетная обработка и скрипты проекта сами по себе не являются риском.
- Совместный порог Jev pass: все пять Noul должны быть `<= 0.20`, и локальная проверка свидетельств должна пройти. scope_conflict оценивает только явные границы, посторонность действия проверяется отдельно; вопрос об учётных данных явно относится к их раскрытию или передаче чувствительных данных во внешнее неразрешённое место. Разрешённая передача не учитывается в этом вопросе, но всё ещё может отмечаться вопросом о внешнем воздействии. Все поля описывают отрицательные риски; routine, совокупный Choice и единый confidence не используются. v2 ещё не прошла повторную калибровку на реальных вызовах; порог нельзя считать гарантией безопасности всего действия.
- Распространённые открытые учётные данные маскируются и внутри строк (Authorization, чувствительные аргументы/присваивания, curl -u/--user, URL userinfo), причём до ограничения длины. Если подозрительные неполные учётные данные нельзя безопасно отделить, выполняется локальный пропуск; покрытие произвольных кодировок не заявляется. Замена статических путей должна проверять обе границы; родительские пути и динамическая конкатенация не должны создавать маркеры внутреннего пути.
- Построение состояния Jev, HTTP-вызов, проверка ответа и объединение вероятностей скрыты за небольшим интерфейсом в `lib/review/jev.mjs`; `lib/review/run.mjs` знает только о необязательном адаптере быстрой проверки. Реализация углублённой проверки остаётся единственной, весь процесс проверки моделью не копируется.
- `executor.gate` по-прежнему представляет одно итоговое событие, совместимое по stage и allow/ask. review-fast + reviewer:jev означает ранний успех; review-fast + reviewer:zcode — успех исходной быстрой проверки; итоговый reviewer для review-slow/review-failed — zcode. Добавляется preScreen с Jev outcome:pass/flag/error/skip и metadata из разрешённого списка (model/schema, probabilities, usage, requestId, attempts, status, durationMs, errorCode/ reasonCode); skip reasonCode принимает evidence_omitted/input_truncated/missing_intent/unsafe_input. Исторический fastReview сохраняет прежний смысл Jev flag/error и не становится результатом ZCode. Значения диагностических полей нужно проверять и маскировать, одной фильтрации ключей недостаточно.
- События, ошибки, pending и runner.log никогда не содержат ключ, Authorization, полное состояние Jev и непроверенное тело ответа. Хотя объект конфигурации, возвращаемый `loadConfig`, содержит ключ, его нельзя целиком сериализовать, печатать или передавать дочернему app-server.
- `doctor` не проверяет Jev через сеть. Сохраняются review.enabled/fastScreen/jevConfigured, добавляется pipeline: при включении с ключом ['jev','zcode-fast','zcode-slow'], без ключа — два последних элемента, при отключении — []. fastScreen сохраняет совместимый смысл первой необязательной проверки и не означает замену исходной быстрой проверки. При ошибке конфигурации все состояния review и pipeline равны null; вымышленный выбор по умолчанию не сообщается. Человекочитаемый вывод объясняет невозможность определить состояние и никогда не показывает ключ.
- Старый контракт `review.enabled:false` сохраняется: вся проверка моделью отключается, после жёстких правил любой запрос переходит в ожидание ответа; Jev не вызывается даже с настроенным ключом. `review.fastMaxTokens` влияет только на резервную быструю проверку ZCode; `review.slowMaxTokens` и `review.timeoutMs` по-прежнему влияют на углублённую проверку ZCode. В первой версии модель Jev, схема, порог, повторы и тайм-ауты заданы константами кода, публичная конфигурация не расширяется.

### Оболочка

- Подкоманды CLI: `doctor、models、list、new、send、follow、status、cancel、approve、deny、answer、quota、watch`; параметры см. в разделе 4 PRD.
- `doctor` не расходует квоту и состоит из пяти шагов (раздел 4 PRD): проверить наличие `config/provider/zcode-builtin.json` рядом с `zcode.cjs` (критерий для 3.12+; до 3.12 — версия ≥ 0.14.8, см. decisions D14); отдельно показать состояние двух источников провайдеров (D19); выполнить реальное рукопожатие — список моделей и распределение уровней по-прежнему вычисляются локально из config.json, рукопожатие лишь сопоставляет возвращённый create `settings.model.available` и предупреждает об отсутствующих, дополнительно сообщая, есть ли у выбранного провайдера открытый apiKey в config.json. Отдельная строка локального состояния показывает цепочку проверки (необязательная предварительная проверка Jev → быстрая проверка ZCode → углублённая проверка); Jev через сеть не проверяется. Шаг ⑤ проверяет внепиковый интерфейс и обращается к сети (D20).
- Имя skill — `zcode-executor`, фразы запуска — «让 zcode 去做» («пусть zcode сделает») и «派给 zcode» («поручи zcode»). Содержание определяется разделом 9 PRD.
- В шаблон файла задания добавляется строка с напоминанием передавать `--task` при отправке.

## Решения по тестированию

**Хорошие тесты** проверяют только внешнее поведение: задать сценарий mock app-server, выполнить одну команду CLI, проверить код завершения, JSON в stdout,
файлы, сохранённые в `runs/`, и последовательность сообщений mock. Внутренние вызовы функций не проверяются.

**Точек подмены только две**, обе используют существующие подходы:

1. **CLI против mock app-server** (основная точка подмены). `test/mock-appserver.mjs` — подставной процесс, говорящий по протоколу app-server через stdio.
   Поведение задаётся JSON-сценарием (что возвращает create, какие события приходят после send, когда поступают запрос разрешения или вопрос, какой метод возвращает ошибку,
   после обработки какого метода происходит сбой). Каждое полученное сообщение добавляется в файл записи для проверок. CLI направляется к нему через переменную окружения.
   Покрытие: все шаги doctor; проверка списка разрешённых каталогов, уровня модели и размышления в new; шесть кодов завершения send --wait; фоновый runner и follow / status;
   порядок очереди и повторная отправка после сбоя; взаимное исключение блокировкой; cancel; форматы ответов и события approve / deny / answer; распределение списка моделей create по уровням.
   Файлы: `test/mock-appserver.mjs` и `test/cli.test.mjs`.
2. **Чистые функции шлюза согласования**. Сопоставление жёстких правил, построение текста инструкции, разбор вывода быстрой и углублённой проверок, автоматическое распределение уровней — функции без побочных эффектов;
   им напрямую подаются фиксированные входные данные и проверяются результаты. Интерфейс `Complete` проверки моделью в тестах заменяется функцией, возвращающей фиксированный текст,
   покрывая allow, преобразование deny в ask, ошибку разбора в ask и исключение вызова в ask.
   `lib/review/` устроен так, чтобы реальное выполнение и автономное воспроизведение использовали одни и те же чистые функции.

В `npm test` не выполняется ни один реальный `session/send`. Реальная проверка проводится вручную по критериям завершения handoff, по одному разу на шаг.

## Примечания

- Факты, требовавшие проверки на реальной установке до начала работы, перечислены в разделе 11 PRD; все проверены, выводы находятся в verified.md.
- Для диагностики см. `~/.zcode/cli/log/zcode-YYYY-MM-DD.jsonl`; подробности ошибок JSON-RPC находятся в `error.data.details`.
- `~/.zcode/v2/config.json` доступен только для чтения и содержит API-ключи.
- Недопустимый уровень размышления в `session/create` не вызывает ошибку, а молча игнорируется, поэтому проверка должна выполняться на клиенте.
