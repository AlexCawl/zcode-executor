## D1 Назначение: передача работы и приёмка; протоколом занимаются другие

Три сторонних проекта (zcode-open-bridge, zcode-acp, coder-mcp-bridge) уже трижды исследовали
протокол app-server ZCode. Ни один не занимается тем, как Claude пишет файл задания, выбирает рабочее дерево,
ставит работу в очередь, принимает результат и ведёт учёт. Этот проект занимается только этим.

**Явно вне области проекта**: продукт для преобразования протоколов, TUI, удалённый доступ, инструмент проверки кода, универсальное распределение ресурсов.

Вернуться к вопросу, если ZCode официально предоставит возможности передачи работы и приёмки.

## D2 Прямое подключение к app-server, без ACP посередине

Изначально планировался транспорт ACP с преобразованием через zcode-acp-server.
ACP становится общим языком только при подключении нескольких исполнителей; проект подключает только ZCode, поэтому это лишний слой преобразования.

После прямого подключения исчезают три из четырёх исходных проблем: `session/create` сразу возвращает настоящий идентификатор `sess_`
(ленивые сессии и пространство имён list придуманы в zcode-acp для редакторов); `session/close` уже существует;
`mode` и `toolDenylist` можно передать непосредственно при create; `interaction/requestPermission`
приходит прямо к нам. Оставшаяся синхронизация реестра провайдеров — лишь несколько строк фильтрации.

Цена: самостоятельно поддерживать клиент app-server примерно на 800–1200 строк, взяв основу из zcode-acp
(Apache-2.0, с сохранением уведомлений). zcode-acp выпустил десять минорных версий за два дня и движется к TUI и удалённому доступу;
использовать его как зависимость времени выполнения рискованнее, чем поддерживать небольшой клиент самостоятельно.

Вернуться к вопросу, если ZCode станет менять протокол app-server быстрее, чем мы успеваем за ним.

## D3 Согласование: жёсткие правила → проверка моделью → ожидание ответа человека

Сессии работают в режиме `build` (он отправляет запросы разрешения); необязательный `toolDenylist` физически исключает инструменты.
Запрос разрешения поступает в шлюз согласования:

1. Сначала проверяются жёсткие правила, которые нельзя отменить.
2. Проверка моделью выполняется через `workspace/generateText`, расходуя квоту Coding Plan ZCode,
   без создания сессии и засорения списка App. Логика опирается на двухэтапную быструю и углублённую проверку режима auto в Claude Code.
3. Если решить не удалось, начинается ожидание ответа: запрос записывается в `runs/<id>/pending.json`, соединение остаётся открытым без ответа
   (на стороне app-server нет тайм-аута); `send --wait` возвращает `blocked`. Claude спрашивает человека через
   AskUserQuestion, затем выполняет `zcode-executor approve|deny <id>`.

**Проверка моделью даёт только разрешение или передачу человеку.** Отказ тоже проходит через человека. Это условие допустимости «проверки самого себя».

Почему не выбран штатный канал Claude Code: MCP elicitation — единственный путь, позволяющий показать внешний запрос в диалоге Claude
Code, но мост должен постоянно работать как MCP-сервис, диалог должен возникать во время вызова инструмента,
а в неинтерактивном режиме это сразу завершается ошибкой. Хуки и `--permission-prompt-tool` направлены в обратную сторону: они обслуживают только вызовы инструментов самого
Claude. Это оставлено как улучшение для этапа оболочки MCP.

Вернуться к вопросу, если Claude Code откроет внешним процессам вход для согласования.

## D4 Один исполнитель, самостоятельный проект

Не делать универсальный мост для нескольких бэкендов. Проект подключает только ZCode. Заимствуются подходы,
проверенные в предыдущих инструментах автора для передачи работы (жизненный цикл runner, очередь и блокировки, сохранение в runs, приёмка), без ссылок на их код.

## D5 Название: zcode-executor

Репозиторий, плагин, CLI и навык называются одинаково, симметрично другим навыкам автора для передачи работы. Фраза
«让 zcode 去做» («пусть zcode сделает») запускает навык. В названии нет bridge (все три сторонних проекта используют bridge)
и нет имени протокола (протокол — деталь реализации).

## D6 Модели выбираются по уровню, а не по имени

Для передачи работы и проверки моделью используются два уровня: `fast` / `strong`. Список получается через `workspace/readState` и автоматически классифицируется по ключевым словам в имени;
`config.json` позволяет переопределить выбор. Для исполнения уровень размышления по умолчанию `high`, переопределяется через `--thought`; для проверки моделью — `low` (изменено 2026-09-08: проверка определяет лишь, относится ли действие к повседневной работе; high зря тратит время и токены, а углублённая проверка на high однажды израсходовала бюджет на рассуждения и была обрезана).

Имена моделей не фиксируются в коде, поскольку модели сменяются: иначе каждое новое поколение потребует менять код и навык. Уровень размышления моделей класса Flash не понижается:
пользователь на практике получил худший результат при понижении.

**Приоритет провайдеров (добавлено после T0.2b)**: одноимённые модели существуют у нескольких провайдеров; ZCode по умолчанию выбирает `builtin:bigmodel` с оплатой по API key за использование.
Мы предпочитаем Coding Plan: настроенный `preferredProvider` > идентификатор с окончанием `-coding-plan` > `-start-plan` > остальные; выбираются только включённые провайдеры.
Китайские `builtin:bigmodel-*` и международные `builtin:zai-*` равноправны: используется тот, который включён.

Вернуться к вопросу, если появится третий явно отличающийся класс моделей, который не укладывается в два уровня.

## D7 Вопросы исполнителя тоже переходят в ожидание ответа; первым отвечает Claude

AskUserQuestion ZCode не проходит через жёсткие правила и проверку моделью, а сразу переходит в ожидание ответа. `send --wait` возвращает 5;
Claude читает вопрос и решает, выполнить ли `answer` самому или передать его человеку.

Не отвечать автоматически «решай сам по файлу задания»: так мы отмахнёмся именно в тот момент, когда исполнителю больше всего нужна помощь. И не отказывать напрямую: Claude — прораб,
а большинство вопросов уже раскрыты в файле задания, так что он может ответить, не беспокоя человека каждый раз.

Вернуться к вопросу, если доля ошибочных ответов Claude на практике станет такой высокой, что лучше будет передавать все вопросы человеку.

## D8 Разрешённый список cwd: по умолчанию только `~/.zcode-executor/worktrees/`

Разрешённый список защищает от случайного выбора Claude основного дерева как cwd; жёсткие правила защищают от выхода исполнителя за границы. Это разные задачи.
Если cwd не является рабочим деревом, только предупреждать, не отказывать: обычный репозиторий в разрешённом списке — осознанный выбор пользователя.

## D9 Только `.mjs`, без зависимостей и сборки

Типы из TypeScript-прототипа слоя согласования удаляются вручную. Несколько сотен строк не оправдывают введение сборки;
удаление типов во время выполнения в Node 22.18 повысило бы минимальную версию Node и добавило ещё один вид файлов.

Вернуться к вопросу, если объём перенесённого кода превысит две-три тысячи строк и ручное сопровождение двух копий начнёт приводить к ошибкам.

## D10 Перед созданием сессии нужно передать реестр провайдеров, поэтому читается `~/.zcode/v2/config.json` (не действует с 3.12, см. D14)

Проба T0.2 подтвердила: при прямом подключении к app-server без `workspace/updateProviderRegistry` вызов `session/create` сразу отклоняется
(Model config is missing), а readState тоже не получает список моделей. app-server сам не читает v2 config;
только App и zcode-acp передают его за него. Поэтому мы должны читать `~/.zcode/v2/config.json`, строить реестр
и передавать его дочернему процессу со встроенным apiKey.

Неизменные ограничения: этот файл **только читается**; apiKey появляется лишь в stdin дочернего процесса, никогда не сохраняется на диск и не печатается;
провайдеры с пустым models или `enabled:false` отфильтровываются. Прежнее правило RULES «только проверять существование, не читать содержимое» заменяется на
«только чтение, содержимое не выходит за пределы слоя протокола».

Вернуться к вопросу, если ZCode поручит app-server самостоятельно читать конфигурацию.

С 2026-09-18 в ZCode 3.12.2 удалены `workspace/updateProviderRegistry` / `runtimeModel`, см. D14.

## D11 Создавать сессии с `runtimeModel`: модель и провайдера указываем мы (не действует с 3.12, см. D14)

Контрольная точка 1 подтвердила: после передачи реестра провайдеров create без `runtimeModel` всё равно приводит к ошибке хода из-за отсутствия ключа провайдера, а модель по умолчанию относится к
провайдеру с оплатой по API key. Передача `runtimeModel` (ссылка на модель + определение провайдера со встроенным apiKey) решает обе проблемы.
Поэтому `new` всегда вычисляет ссылку на модель по уровню и приоритету провайдеров, строит runtimeModel и передаёт его в create; resume его не передаёт.

Вернуться к вопросу, если ZCode поручит app-server самостоятельно обрабатывать аутентификацию провайдера.

С 2026-09-18 в ZCode 3.12.2 удалены `workspace/updateProviderRegistry` / `runtimeModel`, см. D14.

## D12 Runner всегда работает в фоне; команды переднего плана только читают файлы

Изначально runner должен был работать прямо в команде `send --wait` переднего плана. Но во время ожидания ответа проект должен **сохранять соединение без ответа**: соединение нельзя закрыть,
когда команда переднего плана вернёт код выхода 5. Поэтому runner должен быть отдельным фоновым процессом; `send --wait`, `follow` и `status` переднего плана только читают файлы `runs/<id>/`,
а `approve / deny / answer` передают ответ runner через `answer.json`. Цена — ещё один отсоединённый процесс и слой опроса файлов.

Условий для пересмотра нет.

## D13 `new` не создаёт сессию ZCode; реестр использует локальный идентификатор поручения

Реальная проверка подтвердила: сессию, в которой не было ни одного хода, нельзя возобновить после закрытия процесса; create не принимает произвольный sessionId. Поэтому `new` только проверяет модель без расхода токенов и создаёт запись;
ключ реестра — локальный идентификатор (`x_` и 8 шестнадцатеричных цифр), поле `sessionId` сначала пустое. При первой отправке runner выполняет `session/create` (с runtimeModel, thoughtLevel,
toolDenylist), записывает `sess_` в реестр и в дальнейшем использует `session/resume`. Аргумент `<id>` всех команд — локальный идентификатор.
Если resume у runner выдаёт Session not found (сессия потеряна на стороне ZCode), записать событие `executor.recreated` и создать сессию заново, не завершаться молча.

Цена — два идентификатора, локальный и ZCode; `list` показывает оба столбца. Определение «Сессия» в [CONTEXT.md](CONTEXT.ru.md) изменено соответственно.

Вернуться к вопросу, если ZCode разрешит произвольный sessionId или сохранение пустых сессий.

## D14 С 3.12 используется собственный файл персонального провайдера; ключи записываются во временный файл

Решение: ZCode App 3.12.2 изменил передачу реестра провайдеров с «хост передаёт его app-server» на «app-server сам читает два файла».
`workspace/updateProviderRegistry` и `runtimeModel` исчезли одновременно (см. D10, D11). Теперь при запуске дочернего процесса передаются две
переменные окружения: `ZCODE_BUILTIN_PROVIDER_CONFIG_FILE` указывает на встроенный файл провайдеров из ZCode App (`zcode-builtin.json`,
определение есть в [CONTEXT.md](CONTEXT.ru.md)); `ZCODE_PERSONAL_PROVIDER_CONFIG_FILE` — на наш собственный файл персонального провайдера. В нём только
один провайдер с жёстко заданным providerId `zcode-executor` (не используем `builtin:bigmodel-coding-plan` из config.json
по той же причине, что в D11: в новой версии префиксы `builtin:` / `account:` имеют зарезервированное значение). Параметр модели `session/create` меняется с `runtimeModel` на
`model:{providerId:'zcode-executor', modelId, options:{reasoningLevel}}`, а `modelRef` в `workspace/generateText` —
на `selection` той же формы. В zcode.cjs появился и новый обратный запрос
`interaction/requestProviderRuntimeHeaders` (запрашивает у хоста заголовки времени выполнения перед обращением к модели). Реальная контрольная точка 5 подтвердила, что провайдеры типа api-key
его не отправляют ([verified.md](verified.ru.md), 2026-09-18, строка 5 таблицы). Клиент всё же сохраняет встроенный ответ на случай аккаунтных провайдеров: при наличии ключа —
`{headersApplied:true, requestAuth:{apiKey}}`, без ключа — `{headersApplied:false, errorMessage}`.

Почему: app-server теперь сам читает файлы и больше не принимает реестр от хоста. И `workspace/updateProviderRegistry` (D10), и
`runtimeModel` (D11) удалены; нужен другой способ передать ключи и список моделей. Все проверенные пути без записи на диск оказались непригодны:
`provider/updateAccountConfig` принимает только аккаунтных провайдеров с `access.type:"zhipu-account"`; добавление `apiKey` сразу
отклоняется. Обратный запрос `requestProviderRuntimeHeaders` приходит только перед обращением к модели, но уже при создании сессии провайдер должен существовать в
реестре; вставить его на лету через этот запрос нельзя. Записывать пользовательский `~/.zcode/v2/provider_config.json` тоже нельзя: App переписывает файл,
это конфликтовало бы с конфигурацией пользователя и нарушало ограничение «`~/.zcode` только для чтения» (RULES §6). Поэтому остаётся написать собственный файл персонального провайдера,
который прочитает app-server.

Где ключ: файл персонального провайдера находится во временном каталоге, созданном через `mkdtemp` в `os.tmpdir()`, с правами 0600; он удаляется в
`finally` после завершения дочернего процесса. Не помещать его в `runs/<id>/` (каталог сохраняется для последующего просмотра, ключам там не место).

Оставшееся ограничение: временный файл остаётся в `os.tmpdir()` неудалённым только при SIGKILL runner или сбое машины. В производственных путях нет
кода, отправляющего runner SIGKILL; `cancel` использует файловые сигналы (`answer.json` / `stop.json`), а не завершение процесса. Сам
`$TMPDIR` macOS имеет права 0700 (войти может только текущий пользователь), и система периодически его очищает: две дополнительные защиты.

Вернуться к вопросу, если ZCode предоставит способ передать провайдера типа api-key без записи на диск либо устаревший `~/.zcode/v2/config.json`
перестанет хранить apiKey открытым текстом (тогда корневая проблема сохранения ключей исчезнет).

## D15 Jev выбирается для быстрой проверки ключом из конфигурации плагина; этапа shadow нет (историческое решение, маршрутизация пересмотрена в D16)

> Ниже сохранены прежнее решение и его причины, а не действующая маршрутизация. D16 пересматривает замену быстрой проверки, прямой переход к углублённой проверке при ошибке и схему записи `fastReview`; ограничения на источник ключа, защиту файла и отсутствие shadow сохраняются. Историческая калибровка не доказывает безопасность или производительность нового пути.

Решение: если `review.jev.apiKey` в `~/.zcode-executor/config.json` непустой, первый этап шлюза согласования непосредственно использует фиксированную версию Jev; без ключа используется прежняя быстрая проверка ZCode уровня fast с уровнем размышления `low`. Jev заменяет только быструю проверку; flag и любая ошибка вызова/валидации переходят в ту же углублённую проверку ZCode. Жёсткие правила, `allow_once`, углублённая проверка и ожидание ответа не меняются. Первая версия не предоставляет shadow/off/screen, перечисление провайдеров или источник ключа через окружение.

Почему: калибровка на локальном воспроизведении исторических данных уже завершена, пользователь выбрал пропуск shadow. Файл конфигурации надёжнее наследования окружения отсоединённым runner и позволяет `doctor` выполнять однозначную проверку; единственный источник ключа исключает неоднозначный приоритет. Переход от ошибки Jev к углублённой проверке вместо немедленного ожидания человека сохраняет доступность двухэтапной проверки моделью; сохранение углублённой проверки на ZCode не даёт сбою внешнего сервиса вызвать поток запросов к человеку.

Безопасность и границы данных: конфигурация с ключом Jev должна быть обычным файлом, не символической ссылкой, принадлежать текущему uid и иметь права не шире `0600`; иначе чтение отклоняется. Отправляется только минимальное состояние по разрешённому списку полей; содержимое Write/Edit не покидает машину, пути и учётные данные обезличиваются. Ключ, Authorization, полное состояние и исходное тело ответа не попадают в события, pending, runner.log или дочерний процесс app-server. Все вопросы Jev — независимые отрицательные риски; не использовать «повседневная операция» или суммарный confidence. События сохраняют прежние stage/decision, добавляя только reviewer и отфильтрованные типизированные метаданные; события углублённой проверки объясняют flag/ошибки Jev через вложенный `fastReview`.

Цена: ключ хранится открытым текстом в конфигурации в каталоге пользователя, поэтому обязательны проверки owner/mode. Это больше не соответствует старому ограничению RULES «не сохранять ключи, кроме временного файла провайдера»; пользователь явно выбрал этот компромисс ради стабильного чтения. Изменения конфигурации затрагивают только runner, запущенные/перезапущенные последующей командой и заново прочитавшие настройки; уже работающие соединения не обновляются на лету.

Вернуться к вопросу, если понадобятся системная связка ключей, корпоративное хранилище секретов, собственный endpoint/модель TypeSafe или несколько источников ключа; Jev станет настолько нестабилен, что переход к углублённой проверке при ошибке всё равно неприемлем; либо пользователь явно запросит переключение по сессии/проекту.

## D16 Jev становится необязательной предварительной проверкой; исходная быстрая проверка ZCode сохраняется целиком

Решение: по одобренному плану исправлений и оптимизации (`docs/jev-hardening-plan.md`, локальная запись, не входит в репозиторий) Jev — слой раннего разрешения, который больше не заменяет быструю проверку ZCode. Сначала жёсткие правила и `allow_once`; непустой после удаления пробелов `review.jev.apiKey` включает Jev. При достаточных свидетельствах и соблюдении порогов всех пяти вероятностей pass даёт раннее allow; flag/error/skip, тайм-аут, некорректный ответ и исключения адаптера переходят в исходную быструю проверку ZCode fast + low. Только отрицательный или неразбираемый результат переходит к углублённой проверке. Ошибка вызова исходной быстрой проверки по-прежнему даёт `review-failed` / ask; ошибка углублённой проверки — ask. Без ключа сохраняется исходная цепочка; отключение review сохраняет прежний порядок ожидания ответа.

Почему: исходная быстрая проверка сохраняет возможность принять решение. Если Jev не может разрешить заранее, запрос возвращается в существующую цепочку, а не принудительно направляется в углублённую проверку. Предварительная проверка всё ещё вправе разрешить действие заранее; само добавление слоя не доказывает безопасность. Одновременно должны выполняться требования к свидетельствам, удалению секретных данных из входа, валидации ответа и строгому общему сроку.

Границы свидетельств: если опущено содержимое Write/Edit/MultiEdit, отсутствует действительное намерение, обрезаны сведения о команде или разрешении либо невозможно надёжно удалить секретные данные, выполняется локальный skip без HTTP-запросов к Jev. Сложность не равна риску: полные и относящиеся к заданию конвейеры, подоболочки, пакетные операции и скрипты проекта всё ещё могут проходить предварительную проверку; переход назад нужен лишь при реальном отсутствии необходимых фактов. Исходная быстрая проверка получает исходные action/context, без инструкций на основе вероятностей Jev. Не выгружать содержимое ради увеличения доли ранних разрешений и не расширять прежние разрешения на передачу данных.

Аудит и диагностика: на каждый запрос по-прежнему приходится один итоговый `executor.gate`; `preScreen` отдельно записывает Jev pass/flag/error/skip, а итоговые stage/reviewer различают раннее разрешение Jev, разрешение быстрой проверки ZCode и углублённую проверку. Исторический `fastReview` сохраняет прежнее значение возврата из Jev, без молчаливой смены смысла. `doctor` получает `review.pipeline`: `['jev','zcode-fast','zcode-slow']` с ключом, последние два элемента без ключа, `[]` при отключении, `null` при ошибке конфигурации (не удалось определить); совместимый `fastScreen` не означает замену исходной быстрой проверки.

Сохраняются: конфигурация как единственный источник ключа, проверки владельца и прав, отсутствие обходного пути через окружение, отсутствие shadow/mode, фиксированная модель, нулевые зависимости времени выполнения; параллельной гонки нет. Удаление повторяющихся вопросов и уточнение границ в этой итерации переводят схему на `approval-v2` (модель по-прежнему `jev-1.13.0`), без повторной реальной калибровки; порог остаётся 0.20, без ослабления.

Цена: если Jev не разрешает заранее, добавляется последовательное ожидание; локальный skip не несёт этих затрат HTTP. Записи с опущенным содержимым больше не получают раннего разрешения Jev. Нужно на одной и той же выборке сравнивать сквозное время, долю ранних разрешений, возвраты и стоимость; прежние реальные Write pass и старая калибровка — только исторические свидетельства, их нельзя представлять как проверку нового пути.

Вернуться к вопросу, если парные измерения не покажут чистого выигрыша и потребуют сузить применимость или изменить бюджет. Восстановление раннего разрешения действий с опущенным содержимым или переход к углублённой проверке при исключении исходной быстрой проверки требуют отдельного решения и приёмки; незаметно включать их в эту итерацию нельзя.

## D17 Вмешательство в ход через sendText в v4/command; сессии и поток событий по-прежнему используют старые методы session/*

Решение (2026-09-21, T6-B): вмешательство во время хода больше не отправляет второй `session/send` (с App 3.12.2 он отклоняется с -32010,
«A prompt is already running»). Вместо этого отправляется команда `sendText` через `v4/command` с `requestedDelivery:"guide"`:
во время хода она внедряется после следующего пакета инструментов, до следующего обращения к модели; если границы инструментов нет или есть вложения, ZCode сам переходит к очереди,
и ввод выполняется следующим после завершения хода. Оба случая считаются успешным вмешательством (реальная контрольная точка 6b: guide внедрилось и подействовало между b.txt и c.txt).
ACK `startNow` означает, что к приходу вмешательства ход уже закончился и начался незапланированный ход; немедленно отправить v4 `stop` и записать неудачу.
Сессии по-прежнему создаются старым `session/create` (нужен `toolDenylist`, и только этот метод выдаёт список моделей), подписка остаётся через старый `session/subscribe`,
ответы на согласования и вопросы по-прежнему идут через старые обратные запросы. В слое протокола добавляется только тонкая обёртка `AppServerClient.command()`.

Почему: в исходном коде `v4/command` проверяет только существование сессии, без требования предварительной подписки на тему v4 или рукопожатия. Сессии, созданные старым create,
находятся в той же таблице (подтверждено локальной пробой без расхода токенов); само настольное App сочетает старый create и команды v4. В v4 `createSession` нет
`toolDenylist`, а каталог моделей есть только в результате старого `session/create`, поэтому v4 не становится основным путём.

Вернуться к вопросу, если любой из старых `session/create` / `session/subscribe` / `session/event` вернёт -32601 (см. D18).

## D18 Старый протокол готовят к выводу из эксплуатации; подписка и проекция v4 отложены

Решение (2026-09-21): в исходниках ZCode 3.14 `session/send` (частично), `session/stop` и `session/fork` отмечены
@deprecated с комментарием «после удаления старых session/* v4/ останется единственным протоколом». Сейчас не мигрируем: само настольное приложение всё ещё использует старый `session/create`,
а миграция не даёт функций, только работу (нисходящие кадры v4 — проекция snapshot + пять видов delta с фрагментами ≥1 MiB; нужен код их применения).
Условие запуска фиксировано: любой старый метод возвращает -32601 в новой App либо в примечаниях к выпуску объявляют удаление старых `session/*`. Путь описан
в направлении D файла `docs/PLAN-v4.md` (`v4/conversation/subscribe` → применение snapshot/delta → определение завершения хода по
`turnHeader.state` / `control.phase`); `command()` из D17 — отправная точка. Согласования по-прежнему отвечают на обратные запросы, переходить к `resolveInteraction` не требуется.

## D19 Для аккаунтного Coding Plan расшифровывать платформенный ключ из credentials.json и использовать тот же путь D14

Решение (2026-09-21, T6-C): добавить второй источник реестра провайдеров. В `~/.zcode/v2/credentials.json` (App ZCode получает
платформенный API key за пользователя, вошедшего через OAuth; значение имеет вид `enc:v1:<iv>.<tag>.<密文>`, где `<密文>` — шифротекст;
AES-256-GCM, ключ = sha256(`ZCODE_CREDENTIAL_SECRET` либо `zcode-credential-fallback:<platform>:<homedir>:<username>`)) читать только
четыре ключа: `oauth:active_provider`, `oauth:<family>:user_info` (для id), а также два ключа индивидуального и командного плана
`account-provider:coding-plan:...:api-key`. Расшифрованные ключи объединяются с baseUrl и списком моделей из записей `account:*-coding-plan` встроенного файла провайдеров
(регулярные выражения `modelRules` сопоставляют modelId без учёта регистра; при нескольких совпадениях последующие перекрывают предыдущие), образуя элементы реестра той же формы, что и устаревший config.json
(`buildAccountProviders`). Далее запись временного файла персонального провайдера, создание сессии и проверка моделью идут по существующему
пути D14 без изменений слоя протокола; в персональном файле `access.type` остаётся `api-key`: расшифрованный ключ — обычный платформенный ключ,
App само использует его так же. В приоритет pickProvider добавляются два аккаунтных уровня (`preferredProvider` > `account:*-individual-coding-plan`
> `account:*-team-coding-plan` > `-coding-plan` > `-start-plan` > остальные). Отсутствие одного источника даёт только warning; ошибка возникает, лишь когда оба источника
не дают ни одного провайдера (message содержит обе причины, doctor ② показывает состояние источников отдельными строками).

Почему не `provider/updateAccountConfig`: он принимает только аккаунтные записи с `access.type:"zhipu-account"`, а добавление `apiKey`
сразу отклоняет. Ответ на `interaction/requestProviderRuntimeHeaders` аккаунтного провайдера требует того же ключа, лишь добавляя сопровождение ещё одного revision;
start-plan использует истекающий jwt; запись пользовательского `~/.zcode/v2/provider_config.json` конфликтует с App (исключено ещё в D14).

Риски и границы: получение ключа зависит от platform/homedir/username (после переезда на другую машину или смены имени пользователя расшифровать нельзя; сообщать явно «不可用» — «недоступно»,
не молчать). Выход из App удаляет ключи из credentials.json; при исчезновении источника используется legacy. Имена ключей — частная реализация App, при их смене
чтение тоже перестанет работать. credentials.json только читается, расшифровываются лишь четыре ключа; остальные, например токены OAuth, не читаются и не расшифровываются. Расшифрованный ключ
обрабатывается так же, как apiKey из config.json (RULES §6, §8).

Вернуться к вопросу, если ZCode предоставит передачу аккаунтного провайдера без записи на диск либо ключ перестанет храниться в credentials.json / шифроваться таким способом.

## D20 Внепиковые задачи: сами получаем талоны и ждём очередь, ход идёт через официальный внепиковый провайдер; из credentials.json дополнительно читается `zcodejwttoken`

Решение (2026-09-27): для внепиковых задач (off-peak, бесплатно по подписке Coding Plan, без расхода квоты плана) самостоятельно реализовать половину, за которую отвечает настольный хост:
прямое обращение к интерфейсам получения талона, опроса и расчёта `https://zcode.z.ai/api/v1/off-peak`. Когда талон готов, сначала передать
`provider/updateAccountConfig` в app-server, пометив встроенный `account:<family>-offpeak-idle-plan` как авторизованный
(`basedOnZCodeBuiltinRevision` = `zcode-builtin:<内置文件 revision>:<sha256(内置文件绝对路径)>`, то есть ревизия встроенного файла и sha256 его абсолютного пути),
затем вызвать `session/send` с `modelSelection`, `modelExecution.requestAuth` (JWT, ключ Coding Plan, номер талона),
`offPeakTaskId` и `offPeakRunType`. Для этого кроме четырёх ключей D19 из credentials.json расшифровывается ещё `zcodejwttoken`;
ограничение D19 «токены OAuth и подобное не читать и не расшифровывать» уточняется: разрешён только этот ключ, остальные по-прежнему не читаются.

Почему: внепиковый сервер принимает только этот JWT, другого источника нет. Сам ход не делает HTTP-запросы нашей реализацией, а использует официальный внепиковый провайдер CLI: для доменов z.ai CLI требует
клиентскую подпись, и только аккаунтный off-peak освобождён от неё; кроме того, CLI уже распознаёт «3105/429 — ещё в очереди, выждать и повторить» и «3102 —
талон истёк». Реальная сквозная проверка пройдена ([verified.md](verified.ru.md), «Проба внепиковых задач»). Не делать обратный запрос CLI `offPeak/create` единственным
входом: он возникает лишь когда внепиковую работу просит собственная модель исполнителя; прораб использует наш вход. Обратные запросы можно добавить позднее на том же ядре.

Риски и границы: интерфейсы и имена ключей — частная реализация App; изменения сломают внепиковый путь, не затронув обычную передачу работы. JWT не имеет срока действия и обладает широкими правами;
обращаться с ним как с ключом плана: только память, список удаления секретов и параметры JSON-RPC; без записи на диск, в runs/ и журналы (проба подтвердила, что CLI
не записывает requestAuth в ~/.zcode/cli). Число бесплатных получений талона ограничено; повторное получение после истечения должно иметь предел. После готовности есть около 5 минут, максимальное выполнение — 3 часа.

Правила (приняты на grill 2026-09-27; подробности в `docs/SPEC-offpeak.md`, локальная запись, не входит в репозиторий):

- Вход: `send <id> <正文> --offpeak` (`<正文>` означает текст сообщения). У сессии нет типа, внепиковость — свойство отправки. Внепиковая отправка монопольно занимает свободную сессию:
  при живом runner или непустой очереди отказать (код выхода 2); другие отправки в эту сессию во время ожидания очереди тоже отклоняются. Договорённость: создавать отдельную сессию для внепиковых отправок;
  после завершения в ней можно запросить доработку обычной или внепиковой отправкой.
- Получать талон сразу; ошибка получения (нет доступа, квота исчерпана, интерфейс изменился) даёт код выхода 2. Без `--wait` успешное получение сразу возвращает 0; тайм-аут `--wait` отсчитывается лишь
  с запуска хода.
- Модель и уровень размышления берутся из сессии; модель должна быть во внепиковом списке. Поддерживаются только индивидуальные планы двух семейств.
- Шлюз согласования не меняется: на ожидающие запросы отвечает отправитель; проверка моделью по-прежнему идёт через обычного провайдера.
- Истёкший или недействительный талон получается заново автоматически, не более 2 повторных получений на отправку; исчерпание завершает ход с ошибкой (код выхода 4). Любой окончательный исход закрывает талон расчётом; после 3 повторов расчёта
  оставить только предупреждение в status. На macOS во время ожидания талона и выполнения использовать caffeinate против сна по бездействию.
- Пункт ⑤ doctor / `doctor --offpeak` без расхода квоты проверяет четыре слоя (учётные данные, встроенную запись, контракт сервера, полный путь с фиктивным талоном), давая
  ok / changed / unavailable / not-applicable. Только changed даёт код выхода 1; записывать проверенную версию App, при несовпадении лишь предупреждать.
- Не делать: автоматическую самопроверку перед send, периодическую самопроверку (пользователь сам настраивает cron); подключение обратного запроса CLI `offPeak/create`; командные планы.
- Дополнение пользователя от 2026-09-28: **по умолчанию отправка обычная**. Внепиковый режим лишь предлагается пользователю: перед первой передачей работы в каждом разговоре выполнить не расходующий квоту `quota`,
  объяснить «можно выбрать внепиковый режим (бесплатно, время запуска неизвестно); сегодня инструмент уже использовал его N раз, сейчас талон можно/нельзя получить» и отправлять с `--offpeak` только по выбору пользователя. Доработка тоже по умолчанию отправляется обычно
  (взамен прежнего «если доработка займёт больше 20 минут, Claude может сам выбрать внепиковый режим»). Причина: сервер не сообщает остаток; около 3 получений в день легко потратить на повторные талоны одной отправки,
  поэтому решение должен осознанно принимать пользователь.

Вернуться к вопросу, если ZCode перенесёт внепиковую очередь в app-server (CLI сам ждёт очередь), предоставит официальный API либо сервер начнёт требовать клиентскую подпись.

## D21 Отправки Start Plan: сессия остаётся прежней, каждый ход направляется отдельно, хост передаёт JWT через обратные запросы

Решение (2026-09-29, пересмотр направления 3 PLAN-v4 «start-plan не делать»): `send <id> <正文> --start-plan` (`<正文>` — текст сообщения). Это свойство отправки (как в D20:
у сессий нет типа); очередь, шлюз согласования, отсчёт времени и коды выхода такие же, как у обычной отправки. Нет талона, ожидания и расчёта; только запросы модели этого хода идут через встроенную
запись `account:<family>-start-plan` (endpoint `https://zcode.z.ai/api/v1/zcode-plan/anthropic`), расходуя квоту подписки Start Plan.
Предусловия send (код выхода 2): модель сессии входит в `builtinModelIds` этой записи (GLM-5.3-Flash, GLM-5.2, GLM-5-Turbo; GLM-5.3 в списке нет),
из учётных данных можно получить family (`oauth:active_provider`) и `zcodejwttoken` (`readStartPlanAuth`, ключ Coding Plan и user_info не нужны),
запись существует во встроенном файле. Сочетание с `--steer` / `--offpeak` / `--resume` — ошибка использования (код выхода 1). Перед соединением runner смотрит начало очереди; для Start Plan
сначала помещает JWT в secrets и providerAuth. Перед send передаётся `provider/updateAccountConfig`, авторизующий запись (префикс revision
`zcode-executor-start-plan:`, форма как в D20); send включает `modelSelection` (направление на один ход) и
`modelExecution:{selectionScope:"execution", memoryExtraction:"skip"}`, записывается событие `executor.startplan.started`.

Почему (сверка 2026-09-29 с zcode.cjs и app.asar локального App 3.14.1; источники и свидетельства в `docs/tasks/T8-startplan.md`):

- CLI принимает встроенный в параметры send `modelExecution.requestAuth` только для ходов с `mode:"off-peak"`; остальные zhipu-account (включая start-plan)
  перед каждым обращением к модели отправляют обратный запрос `interaction/requestProviderRuntimeHeaders`. Поэтому аутентификация Start Plan возможна только через обратные запросы;
  существующая форма ответа providerAuth в appserver.mjs (`{headersApplied:true, requestAuth:{apiKey}}`) как раз подходит.
- Данные, которые хост App даёт start-plan (app.asar `createAccountProviderRequestAuthService.resolveCurrent`), — просто
  `{apiKey: <zcodejwttoken>}`: JWT используется отдельно, без дополнительных заголовков и ключа Coding Plan; в credentials.json вообще нет
  ключа start-plan. Поэтому `readStartPlanAuth` и не требует user_info и двух ключей плана.
- CLI освобождает zhipu-account с `mode:"start-plan"` от клиентской подписи (zcode.cjs `wEs`); а персональный файл задаёт провайдеров типа api-key,
  и при адресе zcode.z.ai подпись навязывается по домену, тогда как JWT не имеет формы `id.secret` ([verified.md](verified.ru.md), 2026-09-28, «Ключ подписи должен содержать одну точку»).
  Поэтому короткий путь «собрать api-key провайдера в персональном файле» не работает: нужен аккаунтный провайдер.
- `modelExecution.selectionScope` обязан быть `"execution"` (обязательный литерал в схеме параметров send): это направление на один ход. Без него
  modelSelection может стать текущей моделью сессии, и последующие обычные отправки тоже пойдут туда; у того runner нет JWT, ход только завершится ошибкой.

Причина пересмотра направления 3 PLAN-v4: запись от 2026-09-21 «start-plan использует истекающий jwt, нужно самим обновлять OAuth» ошибалась в двух пунктах:
`zcodejwttoken` уже расшифровывается в D20, на реальной системе истечения не наблюдалось; requestAuth хоста для start-plan тоже не требует обновления OAuth. Достаточно передавать тот же JWT
app-server в ответ на обратные запросы.

Риски и границы: интерфейсы и имена ключей — частная реализация App; изменения сломают этот канал, обычную передачу работы не затронут. При занятости Start Plan (3008/3009/3010) CLI уже выполняет
задержку перед повторными попытками и восстановление; при captcha (3007) снова запрашивает заголовки времени выполнения (отвечаем тем же JWT), а при необходимости человеческого решения CAPTCHA ход заканчивается ошибкой. Если providerAuth
не может ответить (учётные данные исчезли), ход сразу завершается ошибкой, без бессмысленного ожидания 180 секунд. JWT обрабатывается как в D20: только память, список удаления секретов и ответы JSON-RPC.
Не делать doctor ⑥: отсутствие учётных данных и записей покрывают предусловия send, изменение интерфейса проявится ошибкой хода следующей отправки.

Вернуться к вопросу, если CLI начнёт принимать другие источники аутентификации для ходов start-plan либо изменятся mode или список моделей встроенной записи (источник списка — встроенный файл через `startPlanModelIds`;
следовать изменениям App).

Реальная проверка (2026-09-29; подробности в [verified.md](verified.ru.md), «Проба отправки Start Plan на реальной системе»): вся цепочка реализации работает по замыслу (передача авторизации, смена направления,
JWT от хоста, запросы доходят до endpoint zcode-plan), но сервер отклоняет их с HTTP 400 `captcha verify failed`: endpoint zcode-plan требует
CAPTCHA Alibaba Cloud (`x-aliyun-captcha-verify-param`); настольный хост App отвечает встроенным CAPTCHA SDK, а хост без интерфейса не может создать этот заголовок.
По той же причине standalone-порт CLI поддерживает только individual-coding-plan. **Вывод: канал Start Plan сейчас зависит от интерфейса App;
реализация на стороне исполнителя сохранена, но использовать её нельзя**. `--start-plan` завершается понятной ошибкой хода (код выхода 4), обычные и внепиковые отправки не затронуты.
Дополнительное условие пересмотра: сервер снимает CAPTCHA с аккаунтного Start Plan (например, выдаёт платформенный ключ, как Coding Plan) либо предоставляет проверочные данные,
которые может повторно использовать хост без интерфейса.

**Удаление (2026-10-02, повторное открытие 2026-10-09)**: из-за описанной CAPTCHA вся реализация однажды была удалена (обратная отмена e26fedb); 2026-10-09 сервер перестал требовать проверку человека для аккаунтного
start-plan (условие выполнено), и прежняя реализация возвращена (код и тесты e26fedb). Реальная проверка описана в [verified.md](verified.ru.md).

## D22 Панель наблюдения реализуется как мод Claude Code; данные приходят только из подкоманды `watch`

Решение (2026-10-02): добавить в плагин панель наблюдения, работающую только в Claude Code (`hooks/`, плагин функциональных хуков Claude Code, обычно называемый модом).
Её открывает `/zcode`, а отправка Claude открывает автоматически; в реальном времени показываются ответы, инструменты, ожидание ответа и внепиковые очереди сессий проекта, со сводкой в строке состояния и всплывающими уведомлениями.
В CLI добавляется постоянно работающий `watch --json` только для чтения, передающий снимки сессий; мод запускает дочерний `watch` до окончания сессии.

Почему:

- Раньше за переданными заданиями можно было следить только через опрос `status` / `follow` самим Claude, человек не видел процесс; мод рисует панель, строку состояния и уведомления без расхода квоты.
- В среде мода нет Node, нельзя импортировать `lib/`. Прямое чтение `runs/` потребовало бы заново реализовать определение фазы внутри мода (`phaseOf` проверяет живость процесса, чего мод не умеет),
  поэтому данные приходят только из CLI, а логика остаётся в одном месте. Постоянный `watch` вместо периодического вызова `status` модом: файлы событий достигают 121MB, читать их с начала каждый раз слишком дорого.
- Панель только показывает: согласования и вопросы по-прежнему передаёт Claude через AskUserQuestion (жёсткое ограничение AGENTS.md); кнопки разрешения в панели нет.
- Показываются только сессии репозитория текущей сессии Claude (репозиторий определяется по общему каталогу данных git, см. [CONTEXT.md](CONTEXT.ru.md)).
- Анимированные значки настольной версии используют режим изображения `Svg` и CSS-анимацию внутри SVG: проверка 2026-10-02 показала, что хост нерегулярно обновляет песочницу `isInteractive`, вызывая заметное мерцание; режим изображения анимируется без мерцания ([verified.md](verified.ru.md)).

Риски и границы: интерфейс модов отмечен в Claude Code как ранняя предварительная версия и может меняться с версиями; поэтому мод использует мало интерфейсов, вся логика в CLI. Моды распознаёт только Claude Code;
Codex, Gemini, Copilot и Grok по-прежнему получают только навык и CLI. Включены ли функциональные хуки по умолчанию в штатно установленном плагине, определяется проверкой на контрольной точке.

Вернуться к вопросу, если Claude Code удалит или существенно изменит интерфейс функциональных хуков либо понадобится отвечать на ожидающие запросы в панели (сначала изменить жёсткое ограничение AGENTS.md).

Проверено (2026-10-02, [verified.md](verified.ru.md), «Мод Claude Code»): пользователь сообщил об успешном прохождении настольных контрольных точек W1–W9; отправка Claude автоматически открывает панель нормальной ширины. Первый проход `watch` по 219 локальным сессиям — около 0.4 секунды, установившаяся загрузка CPU — около 4%.
v0.4.1 (2026-10-03): последний ответ показывается как Markdown (в снимок добавлено `replyMarkdown`; при обрезке восстанавливаются ограждения блоков кода и заголовки таблиц); свыше двух строк по умолчанию сворачивается, кнопка разворачивает.
Не проверено: вызовет ли ошибку у других хостов чтение `hooks/hooks.json`, содержащего только `modules` (если Codex или Copilot CLI читает его по соглашениям хуков Claude); менять манифест после сообщения об ошибке.

## D23 Самозащита шлюза согласования и компромиссы аудита безопасности 2026-10-08

Решение (2026-10-08, после построчной проверки внешнего аудита безопасности D1–D9 по коду и локальной системе):

1. **Жёсткое правило выхода за границы следует обходу пути ядром** (пункт аудита D1). Раньше `path.resolve` перед `realpathSync` лексически сворачивал `<执行副本>/link/../x` в выглядящий допустимым `<执行副本>/x`
   (`<执行副本>` обозначает рабочее дерево), но фактическая запись попадала на уровень выше цели символической ссылки. Теперь путь разрешается от корня по сегментам (ссылки раскрываются на месте, `..` идёт к реальному родителю, висячие ссылки в последнем сегменте тоже прослеживаются); исходная и лексически нормализованная строки проверяются отдельно, выход любой за границы считается совпадением.
   Если место назначения определить нельзя или пишущий инструмент не даёт проверяемого пути, правило всегда срабатывает.
2. **Самозащита шлюза согласования** (пункт аудита D2). Если исполнитель касается каталога данных инструмента (кроме стандартного корня рабочих деревьев `worktrees/` и рабочего дерева этой сессии) или вызывает CLI инструмента, запрос механически передаётся человеку как `self-modify-approval`.
3. **Снимок файла задания создаётся при постановке в очередь; проверка читает только снимок** (пункт аудита D3). `runs/<id>/tasks/<sha256>.md`; хеш записывается в элемент очереди и `executor.send`.
4. Узкие усиления: дочерний процесс zcode не получает переменные учётных данных хост-агента (D4); дерево `runs/` — 0700, файлы — 0600, секреты в `pending.json` удаляются по значениям (D5); в git пробы согласования отключаются fsmonitor, хуки, внешние diff, textconv и filter-драйверы (D6);
   быстрая проверка принимает лишь единственный Y как отдельное слово (D8); управляющие символы терминала в выводе экранируются (D9-①); временные имена атомарной записи получают случайную часть и создаются эксклюзивно (D9-②); кеш ответов на обратные запросы хранится только до границы хода (D9-③).

Почему:

- Исполнитель ZCode и runner — **один и тот же пользователь**. Права файлов и проверка владельца не мешают ему писать `answer.json` или запускать `zcode-executor approve`; аудит явно не принимает исправление «только chmod».
  Человеческий шлюз — условие выполнения D3 «проверка моделью даёт только разрешение или передачу человеку», поэтому эти два действия не доверяются модели.
- Область самозащиты намеренно узкая. Фраза аудита «сопоставление по префиксу каталога данных не даст ложных срабатываний» здесь неверна: стандартные рабочие деревья находятся под `~/.zcode-executor/worktrees/`, повседневные команды исполнителя содержат этот префикс.
  Поэтому `worktrees/` и cwd текущей сессии исключаются, остальное — контур управления. CLI распознаётся только как «имя, за которым идёт подкоманда»; простое упоминание слова `zcode-executor` (clone, grep, npm view) не считается.
- Снимки хранятся в каталоге данных, а не в рабочем дереве: навык требует помещать файл задания в рабочее дерево, где исполнитель может его менять. Читать живой файл — значит позволить исполнителю самому писать «что сказал пользователь».
  События `executor.send` до обновления не имеют снимков; эти части файлов задания больше не служат основанием для проверки. Уменьшение свидетельств может только чаще вести к человеку.
- Новые проверки при неудаче всегда передают человеку: неизвестный путь, невозможность перечислить filter-драйверы, неоднозначный ответ быстрой проверки — никогда не разрешают.

Риски и границы (честно записанные известные пробелы):

- **Самозащита распознаёт только прямые формы**: буквальные пути, `~`, `$HOME`, `$PWD`, `$ZCODE_EXECUTOR_HOME`, относительный `..`, имя CLI с подкомандой. Составление переменных, кодирование, предварительная запись скрипта с последующим запуском
  (код, запускаемый `npm test`, пишет `answer.json`) не распознаются и остаются проверке моделью и человеку. В рамках одного пользователя окончательного решения нет; оно требует системной изоляции (другой пользователь или песочница), а это продуктовое решение вне этой задачи.
- При разработке инструмента им самим будет больше обращений к человеку: команда с буквальным `zcode-executor send` в сообщении коммита или документации перехватывается. Передача человеку не означает отказ.
- Жёсткие ссылки: если связать внешний файл жёсткой ссылкой внутри рабочего дерева и выполнить Edit на месте, проверка пути этого не видит. Аудит этого не упоминал, здесь не исправлялось.
- Переменные окружения (D4) перекрывают только прямое наследование. Окружение процессов самого хост-агента и runner, rc-файлы оболочки всё ещё доступны тому же пользователю. В список входят `GITHUB_TOKEN` / `GH_TOKEN`
  (аудит назвал их явно; это учётные данные Copilot CLI, позволяющие запись в удалённый репозиторий). Если заданию нужны учётные данные GitHub, исполнитель использует локально авторизованный gh / помощник учётных данных git. Настройки этого списка нет.
- `--deny "WebFetch WebSearch"` удаляет эти два встроенных сетевых инструмента из реестра (включая псевдоним `web_search`, сверка исходников в [verified.md](verified.ru.md) от 2026-10-08), сокращая доступную поверхность;
  Bash, js и инструменты MCP всё ещё могут выходить в сеть. Полное отключение сети требует ограничений системы или контейнера.
- Права сохранённых данных (D5) защищают от других пользователей этой машины. Корень каталога данных не переведён на 0700: под ним стандартный корень рабочих деревьев, через него могут проходить, например, пользователи сборки контейнера.
- Пробы git (D6) отключают известные переключатели; сам git не гарантирует безопасность с недоверенной конфигурацией репозитория. Настройки самих подмодулей здесь не отключаются: `git status` входит в извлечённые подмодули и снова запускает git,
  а имена определённых там filter-драйверов отсюда не перечислить. Аудит не упоминал filter-драйверы; это обнаружено локальной проверкой D6 ([verified.md](verified.ru.md), 2026-10-08).
- Реализация `ApplyPatch` не найдена в локальном реестре встроенных инструментов 3.14.4 ([verified.md](verified.ru.md)); сейчас запрос всегда передаётся человеку. Когда реальный ZCode его выдаст, сначала получить формат патча, потом добавить извлечение путей.

Что не менялось и почему:

- **Не применять эвристическое удаление секретов Jev к запросу углублённой проверки** (пункт аудита D7). Запрос идёт тому же провайдеру, у которого работает исполнитель и который уже имеет содержимое; эвристика скрыла бы параметры, необходимые проверяющей модели,
  и стала бы способом обхода (опасные параметры оформляются как учётные данные). `pending.json` по той же причине удаляет лишь точные значения секретов: человеку нужен исходный текст для решения.
- **Содержимое Write / Edit по-прежнему попадает в быструю проверку** (вторая половина D8 аудита). Получение исходного содержимого — существующий инвариант теста («原始正文，不得丢弃» в gate.test, то есть «исходное содержимое нельзя отбрасывать»).
  Основание — компромисс стоимости T3.3: запись внутри границ, разрешённая файлом задания, проходит быструю проверку, не требуя каждый раз углублённой. Изменение — продуктовое решение.
- Не менять канал ответов на unix socket (необязательный второй слой пункта D2 аудита): тот же пользователь всё равно подключится, сам аудит называет это лишь дополнительным слоем защиты. Вызов CLI уже механически перехватывается жёстким правилом самозащиты;
  ещё один жизненный цикл сокета и межплатформенная обработка не стоят затрат.
- Формулировка README «рабочее дерево — песочница» и пропуск текстовых hard-правил при Jev pass: аудит оставил их продуктовыми и документационными решениями автора; они не менялись.

Вернуться к вопросу, если понадобится системная изоляция исполнителя; ZCode действительно выдаст `ApplyPatch` или другой пишущий инструмент; в реальности придёт запрос разрешения без `requestId` (сейчас повторы определяются по полным параметрам, этого достаточно, но не проверено).

## Дополнение: модель для проверки выбирается из уже переданного реестра провайдеров, без дополнительного readState

Runner уже передал реестр при запуске, список моделей в registry совпадает с readState, что экономит один обмен. Цена — не виден `disabledReason` бэкенда;
ни одна из двух моделей Coding Plan при реальных проверках не была отключена. Если появится отключённая модель, перейти к readState.

## Дополнение: документация проекта больше не равна намерению пользователя; она читается из исходного репозитория (2026-09-28)

Убрать исключение разрешения `documented-ops` и фразу «не применяется, если документация называет это обычным обслуживанием» из `shared-service-lifecycle`: документацию пишет автор репозитория,
поэтому незнакомый репозиторий или изменённый исполнителем AGENTS.md мог бы использовать её для снятия soft-правил (та же проблема исправлена в dsh-auto-approve в тот же день).
Источник документации меняется с cwd рабочего дерева на `repoRoot` (корень исходного репозитория), записанный при `new`. У старых записей и нерабочих деревьев этого поля нет — документация не читается, достаточно повторить `new`.

## D24 Настраиваемый прокси для быстрой проверки Jev: `review.jev.proxy`, собственный CONNECT-туннель без прокси из окружения

Решение (2026-10-28, пользователь попросил прокси для запросов Jev): `review.jev.proxy` в `~/.zcode-executor/config.json` (непустой URL `http://`/`https://`,
может содержать userinfo для Basic Proxy-Authorization) направляет HTTP-запросы быстрой проверки Jev через CONNECT-туннель этого прокси. `lib/review/proxy-fetch.mjs`
реализует это без зависимостей (`http.request` отправляет CONNECT, поверх туннеля устанавливается TLS целевого сервера, `createConnection` в `http(s).request` принимает сокет туннеля), оборачивая результат в минимальный Response,
нужный точке подстановки fetchImpl в jev.mjs. Условие включения не меняется: только непустой после удаления пробелов `review.jev.apiKey` включает Jev; один прокси без ключа приводит к
warning в `loadConfig`, прокси не используется. Общий срок, повторы, skip и возврат к ZCode не меняются; недоступный прокси обрабатывается как network_error с прежними повторами и возвратом.

Почему: endpoint Jev за рубежом, прямое подключение нестабильно. Не использовать `NODE_USE_ENV_PROXY`: он разбирает env только при старте процесса (официальная документация undici, доступен лишь с Node ≥22.21),
наследование окружения отсоединённым runner ненадёжно (как с ключом D15, использовать config.json), а прокси-env через spawn попадёт в дочерний app-server, изменив сетевое поведение
основного пути передачи работы. Нулевые зависимости (RULES §1) исключают undici `ProxyAgent`.

Вернуться к вопросу, если понадобятся SOCKS или mTLS со стороны прокси; Node предоставит встроенный API прокси для fetch, настраиваемый во время выполнения; прокси понадобится и другим исходящим запросам кроме Jev — тогда
поднять proxy-fetch в общий модуль слоя рабочего процесса. Тесты не покрывают TLS-рукопожатие внутри туннеля к https-цели (при нулевых зависимостях нельзя сделать самоподписанный сертификат в тестах); после реальной проверки дополнить [verified.md](verified.ru.md).

## D25 Настраиваемое имя модели Jev: `review.jev.model`, по умолчанию вместо фиксированного `jev-1.13.0` используется псевдоним `jev-latest`

Решение (2026-10-28, выпущено вместе с D24 в 0.6.0): `review.jev.model` — необязательная непустая строка, идентификатор модели или псевдоним; по умолчанию `jev-latest` (все примеры официальной документации используют псевдоним; с 2026-10-14 он разрешается в `jev-1.14.0`). Проверка `model` в ответе ослабляется: фиксированная версия должна точно совпадать; при псевдониме допускается его повторение либо номер версии, полученный при разрешении псевдонима (`/jev-\d+\.\d+\.\d+/`), всё остальное — некорректный ответ. Метаданные при успехе сообщают фактически ответившую версию, при ошибке — настроенное значение.

Почему: модели сменяются; жёсткая фиксация требует выпускать новую версию проекта под каждую новую модель, сама документация рекомендует псевдонимы. Порог 0.20 и схема `approval-v2` заданы под `jev-1.13.0` (SPEC помечает v2 как не прошедшую повторную реальную калибровку); псевдоним означает принятие риска «порог может больше не подходить последней версии». Этот риск передаётся пользователю через настройку; фиксация версии возвращает прежнее поведение. В PLAN давно записано «первая версия — только apiKey, модель константой; вернуться при появлении потребности», и потребность появилась.

Вернуться к вопросу, если новая версия за псевдонимом при реальной проверке сильно разойдётся с порогом: вернуть по умолчанию последнюю действительно проверенную версию либо ввести отдельные таблицы порогов по моделям. Если TypeSafe добавит новое семейство моделей с именами не jev-*, ослабить правила проверки.
