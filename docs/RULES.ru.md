# RULES — правила разработки

[English](RULES.md) · [中文](RULES.zh-CN.md) · Русский

> Прочитайте перед написанием кода. Правила учитывают особенности проекта: скрипты Node без зависимостей, один протокол stdio, файлы на диске как состояние
> и расходы при каждой отправке на реальном устройстве. Если правило мешает работе, сначала измените этот файл, затем делайте исключение.

## 1. Язык и структура

- Node ≥ 22, ESM, расширение `.mjs`. Без TypeScript и этапа сборки. Исключение: `types/index.d.ts` описывает типы состояния модуля панели наблюдения только для `claude plugin validate` и не участвует в выполнении.
- Ноль зависимостей времени выполнения. Перед добавлением зависимости запишите обоснование в decisions.md. Тестовые фреймворки тоже не добавляются: используйте `node --test`.
- Размещайте файлы по таблице слоёв AGENTS.md: протокол — `lib/appserver.mjs`, `lib/session.mjs`, `lib/providers.mjs`, `lib/offpeak-provider.mjs`, `lib/scrub.mjs`;
  рабочий процесс — `lib/config.mjs`, `lib/credentials.mjs`, `lib/offpeak.mjs`, `lib/offpeak-check.mjs`, `lib/offpeak-send.mjs`, `lib/offpeak-run.mjs`, `lib/registry.mjs`, `lib/tiers.mjs`, `lib/models.mjs`, `lib/runs.mjs`, `lib/queue.mjs`, `lib/run.mjs`, `lib/intent.mjs`, `lib/tool-summary.mjs`, `lib/snapshot.mjs`;
  шлюз — `lib/gate.mjs`, `lib/pending.mjs`, `lib/review/`; оболочка — `bin/`, `lib/cli/`, `skills/`, `templates/`, `hooks/`.
  `hooks/` — модуль Claude Code в собственном окружении движка, без Node: не импортирует `lib/`, получает данные только из подкоманды `watch`. Проверяемые чистые функции размещаются в `hooks/view.mjs` и тестируются через `node --test` (decisions D22).
  Между слоями общий только `lib/errors.mjs` (`ExecutorError`). Перед созданием файла определите его слой.
- Зависимости направлены только вниз: оболочка → рабочий процесс → протокол. Рабочий процесс вызывает шлюз, а шлюз зависит только от протокола. Слой протокола не знает о
  `runs/`, реестре и кодах завершения. Исключение: оболочка может напрямую использовать **чистые функции** шлюза (`readPending`, `optionClass`, `questionResponse`),
  чтобы CLI и runner разделяли одни правила сопоставления без промежуточных вызовов через рабочий процесс.
- Один файл — одна ответственность. Если файл превышает пятьсот строк, сначала подумайте о разделении, а не о добавлении кода.
- Имена файлов — строчные с дефисами; идентификаторы — camelCase; константы — UPPER_SNAKE. Класс нужен только для хранения состояния, например для клиента протокола.

## 2. Терминология

- В коде, выводе и документации используются термины [CONTEXT.md](CONTEXT.ru.md): session, task file, send, turn, permission request,
  question, gate, hard rule, review (проверка моделью), pending, tier, thoughtLevel.
- Не вводите judge, verdict (результат проверки моделью называется review result), run (имя каталога сессий `runs/` сохранилось исторически; понятие Run
  в код не вводится), prompt (для передачи работы используется send, для текста промпта — promptText).
- Вывод для человека пишется по-китайски; идентификаторы, типы событий и имена полей JSON — по-английски.

## 3. Стиль кода

- Отступ — два пробела, одинарные кавычки, точки с запятой. Жёсткого ограничения длины строки нет: одна мысль на строку, без горизонтальной прокрутки. Не добавляйте форматтер; перед коммитом запускайте `node --check`.
- Предпочитайте `export function`; на верхнем уровне модуля не должно быть действий с побочными эффектами: чтения файлов, запуска процессов.
- Без `default export`.
- Единый тип ошибок — `ExecutorError` с `exitCode`. Сообщения пишутся по-китайски и объясняют дальнейшие действия, например:
  «会话不在登记簿里，用 `zcode-executor list` 看有哪些» («сессии нет в реестре; доступные сессии можно посмотреть через `zcode-executor list`»). Не используйте обрывки в стиле трассировки стека.
- Не подавляйте ошибки. Повторно выбрасывайте перехваченную ошибку, если не обрабатываете её; намеренное игнорирование объясняйте одной строкой комментария.
- Для ошибок JSON-RPC сохраняйте `error.data.details`: `message` содержит лишь краткое описание, недостаточное для диагностики.
- Везде используйте `async` / `await`, не смешивайте с `.then`. Ожидание дочерних процессов и файлов должно иметь тайм-аут.

## 4. Комментарии

- В начале файла — абзац об ответственности файла, о том, что он явно не делает, и с чем взаимодействует.
- Внутри кода комментарии объясняют «почему», а не «что». Очевидное из кода не комментируется.
- Для фактов с реального устройства указывайте источник и дату: `// verified.md 2026-09-07：未答的反向请求每秒重发一次` («обратные запросы без ответа повторяются каждую секунду»).
- Для заимствованного кода указывайте в начале источник, версию и лицензию; добавляйте запись в `NOTICE`. Изменённые места помечайте `// 改：…` («изменено»).
- Намеренные упрощения помечайте `// 权宜：<现在的上限>，<什么时候要升级成什么>` («временное решение: текущее ограничение; когда и как расширить»), например
  `// 权宜：无信号不兜底，真机挂死过一次再加超时` («без сигнала запасного механизма нет; тайм-аут добавим после первого реального зависания»). Упрощение без указанного ограничения — недостаточно продуманное решение.
- Не оставляйте TODO. Будущая работа записывается в `docs/PLAN.md` (локальные записи) или отложенные пункты decisions.md.

## 5. Вывод и коды завершения

- stdout содержит только результат: понятное человеку резюме либо по одному объекту JSON на строку при `--json`. Прогресс, предупреждения и `--stream` направляются в stderr.
- Весь вывод идёт через `process.stdout` / `process.stderr`, включая `console.*`. Точка входа оборачивает эти потоки и заменяет управляющие символы терминала буквальной записью `\uXXXX` (`lib/cli/terminal.mjs`):
  имена инструментов, причины, ответы модели и имена файлов контролирует исполнитель. Нельзя обходить обёртки прямой записью в дескрипторы: `fs.writeSync(1, …)` или дочерние процессы с `stdio: 'inherit'`.
- Каждое сообщение stderr занимает одну строку и начинается с команды или этапа: `new: cwd 不是 worktree，照常建` («cwd не является рабочим деревом; создаём как обычно»).
- Структуры `--json` могут только получать новые поля: удаление полей и изменение их смысла запрещены. Изменения отражаются в разделе 4 PRD.
- Коды завершения фиксированы: 0 / 1 / 2 / 3 / 4 / 5, значения описаны в PRD. Новые ситуации относятся к существующим кодам, новые коды не вводятся.

## 6. Состояние на диске

- Каталог данных определяется из конфигурации один раз; все пути абсолютные.
- JSON сначала записывается во временный файл в том же каталоге, затем выполняется `rename`, чтобы читатель не увидел неполный файл. Имя временного файла содержит случайную часть, создание — исключительное (`wx`): предсказуемое имя можно заранее занять символической ссылкой.
  Используйте `writeJsonAtomic` / `writeFileAtomic` из `lib/config.mjs`, не составляйте временные имена самостоятельно. Для `pending.json` в слое шлюза есть аналогичная реализация: импортировать слой рабочего процесса он не может.
- Файлы инструмента имеют права 0600, `runs/` и вложенные каталоги — 0700 (`PRIVATE_FILE_MODE`, `PRIVATE_DIR_MODE`, `ensureRunsDir` в `lib/runs.mjs`). Права корня каталога данных не ужесточаются: там же по умолчанию находится корень рабочих деревьев.
  Это защита от других пользователей машины. Исполнитель и runner работают от одного пользователя; от исполнителя защищает шлюз (§8).
- `events.jsonl` только дополняется, по одному объекту на строку; `type` собственных событий проекта начинается с `executor.`.
- Время записывается строками ISO 8601 UTC.
- `runs/` и `worktrees/` не хранятся в репозитории; тесты создают временные каталоги через `mkdtemp` и удаляют их в `after()`.
- `~/.zcode/v2/config.json` только читается. Полученный apiKey записывается лишь в персональный файл провайдера с правами 0600 во временном каталоге mkdtemp
  (decisions D14); файл удаляется при завершении дочернего процесса и никогда не попадает в `runs/`, журналы или вывод.
- `~/.zcode/v2/credentials.json` также только читается. Расшифровываются лишь четыре ключа для coding plan аккаунта; внепиковая отправка дополнительно расшифровывает `zcodejwttoken` (D20, только память и параметры JSON-RPC, без записи на диск). Остальные ключи не читаются и не расшифровываются.
  Расшифрованные ключи обрабатываются так же, как apiKey из config.json (decisions D19).

## 7. Слой протокола

- Каждый запрос имеет тайм-аут; его истечение считается ошибкой с указанием метода.
- Обратные запросы дедуплицируются по `params.requestId`; при отсутствии requestId — по методу и полным параметрам. Параметры повторного запроса совпадают дословно; другие параметры означают другой запрос.
  Готовые ответы хранятся только до границы хода и удаляются в начале `Session.send`: повторное использование requestId не должно разрешать новый запрос ответом из прошлого хода. На запрос без обработчика возвращается ошибка `-32601` и строка stderr;
  оставлять его без ответа нельзя: другая сторона повторяет запрос каждую секунду. **Исключение**: запросами разрешений и вопросами управляет слой сессий; без обработчика они намеренно остаются без ответа, приостанавливая ход в ожидании ответа.
  Для каждого такого запроса сохраняются только последние 5 идентификаторов конвертов; ответ отправляется только на них. На реальном устройстве этого хватило для approve после 75 секунд ожидания.
- Неизвестные типы событий сохраняются без изменений и без ошибки.
- Ответ на запрос разрешения имеет форму `{decision:'allow'|'deny'}` (раздел согласований verified.md). До разрешения проверьте наличие в options элемента с `kind` = `allow_once`; иначе передавайте человеку.
- Весь stderr дочернего процесса направляется в stderr текущего процесса с префиксом `zcode:`.
- Не передавайте дочернему zcode переменные окружения с учётными данными хостового агента (`HOST_CREDENTIAL_ENV` в `lib/appserver.mjs`), независимо от того, пришли они из окружения процесса или из `env` вызывающей стороны.
  Новые имена добавляются в эту таблицу. Не заменяйте её разрешающим списком: пропуск вроде `HOME` или `PATH` ломает работу.

## 8. Минимальные требования безопасности, которые нельзя обходить в коде

- У проверки моделью только два исхода: allow и ask. В коде нет ветки отправки deny в zcode, кроме явных команд человека `deny` и `cancel`.
- `approve` разрешает действие только при наличии `allow_once` в options и только однократно. «Всегда разрешать» не реализуется. Используйте `hasAllowOnce` из `lib/pending.mjs`
  для разрешения шлюзом, сохранения ожидающего запроса и `approve`; не создавайте три независимые проверки.
- Runner принимает из `answer.json` только ответ с requestId текущего ожидающего запроса; несовпадения отбрасываются. Ответ предыдущего хода не должен разрешать новый запрос.
- Разрешённые корни проверяются при `new` и повторно по cwd из реестра при запуске runner.
- API-ключи, токены и подобные строки никогда не выводятся. Запись допустима только в двух местах: временный персональный файл D14 с правами 0600 и явно заданный пользователем `review.jev.apiKey` в `~/.zcode-executor/config.json` (D15; файл с ключом должен принадлежать текущему uid, быть обычным файлом, не символической ссылкой, с правами не шире 0600). `doctor` сообщает только о наличии настройки ключа, не выводит сам ключ.
- Жёсткие правила — константы кода, не конфигурация. Два механических правила, выход за рабочее дерево и самозащита, находятся в `lib/review/hard.mjs`: новая проверка при сбое обязана передавать запрос человеку, неопределённость считается совпадением. Нельзя менять путь ask на автоматическое разрешение или отказ.
- При проверке границ нельзя сначала лексически сворачивать путь: `path.resolve`, `path.normalize`, `fs.realpathSync` (его JS-реализация начинается с `path.resolve`) сворачивают `link/..`,
  а ядро сначала переходит к цели ссылки, затем поднимается на уровень. Используйте покомпонентный разбор из `hard.mjs`.
- Обращение исполнителя к каталогу данных инструмента или вызов его CLI механически передаётся человеку (`lib/review/self-guard.mjs`). Распознаются только явные формы; охват не расширяется: рабочие деревья по умолчанию лежат внутри каталога данных, и широкая проверка создаёт массу ложных срабатываний (decisions D23).
- Проверка моделью читает намерение только из снимка задания, сохранённого при постановке в очередь (`runs/<id>/tasks/`), а не из оригинала в рабочем дереве, доступного исполнителю для изменения.
- Процессы, которые runner сам запускает в рабочем дереве (git для проверочных проб), не проходят через шлюз. Все настройки репозитория, способные запускать программы, отключаются параметрами командной строки (`GIT_SAFE_OPTIONS` и `filterOverrides` в `lib/review/evidence.mjs`).

## 9. Тесты

- Один тест на каждое внешнее поведение. Имя описывает поведение, а не реализацию: «cwd за пределами разрешённых корней даёт код завершения 2».
- Проверяются коды завершения, JSON в stdout, файлы на диске и файлы записей mock. Не проверяется число вызовов внутренних функций.
- Тесты работают только с `test/mock-appserver.mjs` и `test/mock-offpeak.mjs` (внепиковый сервис). `npm test` ни при каких условиях не обращается к реальному устройству и не расходует квоту.
- Скрипты для реальных устройств находятся в `scripts/`, имя содержит `real-`. Скрипт с расходом квоты перед запуском выводит «这次会花额度» («этот запуск расходует квоту») и требует `--yes`.
- Тесты с фоновыми процессами в `after()` завершают через SIGKILL все процессы, включая потомков; mock сам завершается при EOF на stdin.
- JSON сценариев хранится рядом с тестом, без отдельного каталога fixtures.
- При изменении протокола сначала меняется mock, затем клиент: mock должен оставаться копией поведения реального устройства. Для полей сценария указываются соответствующие подтверждённые факты.

## 10. Коммиты

- Одна задача занимает один или несколько коммитов; каждый должен самостоятельно проходить `npm test`.
- Сообщения коммитов пишутся по-китайски. Первая строка — `<范围>: <做了什么>` («область: изменение»); область — слой или команда: `协议: 反向请求按 requestId 去重` («протокол: дедупликация обратных запросов по requestId»),
  `send: --wait 超时改为发 session/stop` («send: при тайм-ауте --wait отправляется session/stop»). Тело объясняет причину, не пересказывает diff.
- Не коммитьте `runs/`, `worktrees/`, журналы и временные каталоги.
- Разработка ведётся прямо в основной ветке; задания исполнителя выполняются в ветках `task/T-<编号>` и сливаются после приёмки (`<编号>` означает номер).

## 11. Документация

- При изменении поведения сначала исправьте [PRD.md](PRD.ru.md) или [SPEC.md](SPEC.ru.md), затем код.
- Новые факты с реального устройства записываются в [verified.md](verified.ru.md) с датой и версией.
- Компромиссы фиксируются в [decisions.md](decisions.ru.md): решение, причина, условия пересмотра.
- Новый термин сначала добавляется в [CONTEXT.md](CONTEXT.ru.md), затем используется.
- Заимствование кода требует обновления `NOTICE`.
- По завершении задачи отметьте её в `docs/PLAN.md`; в конце этапа запишите результаты контрольной точки в соответствующий handoff. Оба файла — локальные записи, не хранящиеся в репозитории.
