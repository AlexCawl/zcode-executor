## 1. Какую проблему решаем

Claude Code чётко формулирует задачу разработки, а локальный ZCode (GLM) изменяет код. Между ними нужен канал,
который позволяет передать задание файлом, выполнить его в изолированном рабочем дереве, получить ответ человека или модели на запросы разрешения исполнителя,
а затем принять результат по `git diff` и тестам, а не со слов исполнителя.

**Пользователь**: сам владелец локального настольного ZCode App. Один пользователь, локальная работа; удалённый доступ и многопользовательская изоляция не рассматриваются.

**Вне объёма**: продукт для преобразования протоколов, TUI, удалённый доступ, инструмент проверки кода, общее планирование ресурсов, синхронизация со списком задач ZCode App, оболочка MCP.

Код из zcode-acp сохраняет уведомление Apache-2.0 и указывается в `NOTICE`.

## 3. Полный порядок передачи работы

Исходные обозначения в командах сохранены: `<主仓>` — основное дерево репозитория, `<执行副本>` — рабочее дерево исполнителя, `<仓库名>` — имя репозитория, `<档>` — уровень размышления; `工具` — инструмент. Сообщение в примере `执行 tasks/T-xxx.md` означает «выполни tasks/T-xxx.md».

1. Claude записывает задание в `tasks/T-xxx.md` (шаблон `templates/task.md`); критерии приёмки должны проверяться машиной.
2. Claude самостоятельно выполняет две команды git и создаёт рабочее дерево в разрешённом каталоге:
   `git -C <主仓> worktree add ~/.zcode-executor/worktrees/<仓库名> -b task/T-xxx`; при первом использовании устанавливает зависимости.
3. `zcode-executor new --cwd <执行副本> --title T-xxx [--tier fast|strong] [--thought <档>] [--deny "工具 工具"]`
   → В реестре появляется запись, возвращается локальный идентификатор (`x_…`). Сессия zcode создаётся только при первой отправке (D13).
4. `zcode-executor send <id> "执行 tasks/T-xxx.md" --task <执行副本>/tasks/T-xxx.md --wait`
   → Ожидание на переднем плане; либо без `--wait` — работа в фоне с наблюдением через `follow` / `status`. Относительный путь в сообщении предназначен для чтения исполнителем,
   а `--task` задаёт основание полномочий для проверки моделью и требует абсолютного пути.
5. Если в ходе работы исполнитель запрашивает разрешение, шлюз согласования сначала проверяет жёсткие правила, затем запускает проверку моделью; если решение не принято, запрос переходит в ожидание ответа.
   `send --wait` сразу возвращает код 5 и выводит содержимое ожидающего запроса.
   Claude читает его: запрос разрешения передаёт человеку через AskUserQuestion, затем вызывает `approve <id>` или `deny <id>`;
   на вопрос отвечает через `answer <id> <值>`, если знает ответ (`<值>` — значение), иначе спрашивает человека. Ход продолжается с места ожидания.
6. После окончания хода Claude проводит приёмку: исполнитель не создаёт коммиты, изменения остаются в рабочем каталоге рабочего дерева, поэтому сначала
   `git -C <执行副本> add -A`, чтобы включить новые файлы, затем просмотр `git -C <执行副本> diff --cached` и запуск тестов в рабочем дереве.
7. Если результат принят, Claude создаёт коммит в рабочем дереве и выполняет слияние из основного дерева через `git -C <主仓> merge`;
   иначе снимает изменения с индекса командой `git -C <执行副本> reset`, пишет `tasks/T-xxx-fix.md` и повторяет отправку в ту же сессию.

## 4. CLI

Имя команды — `zcode-executor`. Контракт и коды выхода соответствуют другим инструментам передачи работы этого автора, чтобы Claude осваивал одну систему соглашений.

Исходные обозначения аргументов сохранены: `关键字` — ключевое слово, `绝对路径` — абсолютный путь, `档` — уровень размышления, `工具…` — инструменты, `正文` — текст сообщения, `文件` — файл, `秒` — секунды, `值…` — значения.

| Команда | Назначение |
| --- | --- |
| `doctor [--offpeak] [--json]` | Пять шагов самопроверки без расхода квоты: ① найти `config/provider/zcode-builtin.json` рядом с `zcode.cjs` (признак 3.12+; если файла нет, предложить обновить ZCode App) → ② сообщить состояние обоих источников провайдеров (вход в аккаунт через `credentials.json`, резервный источник `config.json`) и выбранного провайдера → ③ выполнить настоящее рукопожатие (ноль токенов), сообщить уровни моделей и наличие ключа провайдера → ④ показать цепочку проверки для вновь запущенного runner (необязательная предварительная проверка Jev → быстрая проверка ZCode → углублённая проверка; только чтение конфигурации, без сетевого запроса к Jev) → ⑤ самопроверка внепикового API: обращается к сети и запускает внепиковый ход с фиктивным талоном (сервер сразу отклоняет, квота не расходуется), см. «Отправки во внепиковое время» ниже. `--offpeak` запускает только ⑤ |
| `quota [--json]` | Сегодняшнее получение внепиковых талонов: без расхода квоты, запуска app-server и получения нового талона. Сколько раз инструмент получал талон сегодня (считаются события получения и повторного получения в `runs/*/events.jsonl` после сегодняшней полуночи по локальному времени машины; файлы, изменённые до сегодняшнего дня, пропускаются целиком, нечитаемые файлы пропускаются с одной строкой в stderr; использование через App не учитывается; примерно 3 раза в день — наблюдаемое значение) + разрешает ли сервер получить талон сейчас (если нет — локальное время следующей возможности). Для человека — одна строка; `--json` — `{usedToday, estimatedDailyLimit, canTakeNumber, nextTakeAt, state, reason}`, у `state` те же четыре состояния, что в doctor ⑤. Только «API изменился» даёт код 1, исчерпание квоты — тоже 0 (см. «Отправки во внепиковое время» ниже) |
| `models [--json]` | Локально вычислить доступные модели из двух источников (аккаунт: ключ, расшифрованный из `credentials.json`, и таблица моделей встроенного файла провайдеров; legacy: `~/.zcode/v2/config.json`; с 3.12 `workspace/readState` удалён, рукопожатие не выполняется), показать уровни размышления каждой модели и автоматически назначенный уровень модели |
| `list [--project 关键字] [--json]` | Список сессий из реестра: идентификатор, заголовок, cwd, уровень, последний результат, наличие ожидающего запроса; каждая строка `--json` содержит соответствующий репозиторий `repo` |
| `new --cwd <绝对路径> [--title T] [--tier fast\|strong] [--thought 档] [--deny "工具…"] [--provider id] [--json]` | Создать сессию. cwd должен входить в список разрешённых путей; если это не рабочее дерево, только предупредить, не отклонять |
| `send <id> <正文\|-> [--task 文件] [--wait] [--steer] [--timeout 秒] [--stream] [--json]` | Отправка. По умолчанию ставится в очередь; `--steer` через `sendText` (guide) метода `v4/command` добавляет указание в текущий ход на следующей границе вызова инструмента; если границы нет, указание выполняется после завершения хода, не прерывая его |
| `send <id> <正文\|-> --offpeak [--task 文件] [--wait] [--timeout 秒] [--stream] [--json]` | Внепиковая отправка: сразу получить талон, затем при его готовности запустить работу на бесплатных внепиковых ресурсах, без расхода обычной квоты плана (см. «Отправки во внепиковое время» ниже). Не совмещается с `--steer` |
| `send <id> <正文\|-> --start-plan [--task 文件] [--wait] [--timeout 秒] [--stream] [--json]` | Отправка Start Plan: запускается сразу, как обычная отправка, но запросы модели только этого хода используют квоту подписки Start Plan (см. «Отправки Start Plan» ниже). Не совмещается с `--steer` и `--offpeak` |
| `send <id> --offpeak --resume [--wait] [--stream] [--json]` | После завершения хода в состоянии exited или сбоя runner перезапустить только runner и продолжить внепиковую отправку из очереди, без повторной постановки и получения талона |
| `follow <id> [--timeout 秒] [--stream] [--json]` | Наблюдать за фоновым runner; завершиться, когда он запишет новый результат |
| `status <id> [--tools N] [--json]` | Снимок только для чтения: фаза (`running` выполняется / `idle` очередь пуста / `pending` ожидание ответа / `exited` штатное завершение / `stale` runner исчез в процессе), последние вызовы инструментов, длина очереди, последний результат, длительность ожидания ответа; `--json` содержит соответствующий репозиторий `repo`, каждый элемент `tools[]` — краткие параметры `summary` |
| `cancel <id>` | Остановить: сначала отказать ожидающему запросу, затем `session/stop`, после этого не брать новые элементы очереди |
| `approve <id>` | Ответить на текущий ожидающий запрос разрешения только через `allow_once` |
| `deny <id>` | Ответить отказом на текущий ожидающий запрос разрешения |
| `answer <id> [--] <值…>` | Ответить на текущий ожидающий вопрос: варианты сопоставляются по value, label или номеру, несколько значений передаются через запятую в одном аргументе; без вариантов используется свободный текст. Перед значением, начинающимся с `--`, поставить разделитель `--` |

Коды выхода:

| Код | Значение |
| --- | --- |
| 0 | Ход завершён, можно проводить приёмку |
| 1 | Ошибка использования или zcode не запускается (включая ZCode App версии ниже 3.12: встроенный файл провайдеров не найден) |
| 2 | Отказ: путь вне списка разрешённых, сессии нет в реестре, недопустимый уровень модели или размышления; внепиковая отправка отклонена до или во время получения талона (сессия занята, модель отсутствует во внепиковой таблице, нет входа в аккаунт или используется командный план, нет права на внепиковую работу, квота исчерпана, ошибка авторизации при получении талона (401/403, нужно снова войти в App), внепиковый сервис временно недоступен, внепиковый API мог измениться); не выполнены условия Start Plan (модели нет в таблице start plan, нет входа в аккаунт, во встроенном файле нет записи start plan); обычная отправка, пока сессию занимает внепиковая отправка, и `--steer` во время ожидания талона; `--resume` без восстанавливаемой внепиковой отправки |
| 3 | Истёк срок `send --wait`: текущий ход отменён, сессия сохранена и допускает новую отправку; `follow --timeout` по истечении срока только завершает наблюдение, ничего не отменяя |
| 4 | Нештатный ход: `turn.failed`, прерывание или достижение предела вывода |
| 5 | Ожидание ответа человека: запрос разрешения или вопрос |

- `--wait` по умолчанию равен 1800 секундам (config `waitTimeoutSec`), по истечении срока текущий ход отменяется. Ожидание ответа не считается тайм-аутом: сразу возвращается 5.
- В выводе `--json` поле `id` — локальный идентификатор поручения, `sessionId` — `sess_` zcode (null до первого хода), одинаково для всех команд.
- По окончании `send --wait` и `follow` выводятся два блока: «闸门：放行 N 次（红线挂起 a、快筛 b、慢判 c、转人工 d）» (шлюз согласования: разрешено N раз; ожидание по жёсткому правилу a, быстрая проверка b, углублённая c, передача человеку d) и «改动：文件列表；Bash 条数» (изменения: список файлов; число команд Bash); в `--json` им соответствует `summary:{gate:{allow, ask, hard, fast, slow}, files:[…], bashCount}`.
- В `status` каждый недавний вызов инструмента — отдельный элемент с краткими параметрами: `Bash(npm test)`, `Edit(src/a.mjs)`; без кратких параметров — только имя инструмента. В конце строки ожидающей сессии в `list` стоит «挂起: 工具名» (ожидание ответа: имя инструмента).
- У сессии одновременно не более одного ожидающего запроса (разрешения запрашиваются последовательно в рамках хода). Именно на него отвечают `approve` / `deny` / `answer`.
- До создания сессии значение `--thought` проверяется по допустимым уровням этой модели; недопустимое значение даёт код 2 (`session/create` молча игнорирует ошибочное значение, полагаться на его ошибку нельзя).
- Для чтения сообщения из stdin указать `-`. `--json` даёт структуру для машинной обработки.
- В выводе (stdout, stderr, `runner.log`) управляющие символы терминала — C0 (кроме перевода строки и табуляции), DEL, C1, символы управления двунаправленным текстом — заменяются буквальным `\uXXXX`:
  имена инструментов, причины, вопросы, ответы моделей и имена файлов контролирует исполнитель; вывод без преобразования позволяет очистить экран или переписать строку ожидающего запроса, которую читает человек. Смысл `--json` сохраняется (экранирование находится в строке JSON, разбор восстанавливает исходные символы).
- Код выхода `doctor` и `--json.ok`: если не пройден любой шаг ①–③ или вывод ⑤ — «API изменился» (changed), `ok` равен false, код выхода 1; остальные три вывода ⑤ (норма, временно недоступно, неприменимо) на них не влияют. До добавления ⑤ значение `ok` зависело только от ①–③ (⑤ учитывается с 2026-09-27). `--json` добавляет `offpeak: {state, layer, expected, actual, reason, logid, appVersion, verifiedAppVersion}`; `doctor --offpeak --json` выводит только `{ok, offpeak}` (кроме того, при неверной переменной адреса тестового внепикового сервиса `ZCODE_EXECUTOR_OFFPEAK_ORIGIN` команда `doctor --offpeak` также завершается кодом 1).

### Отправки во внепиковое время

Спецификация — в `docs/SPEC-offpeak.md` (локальная запись, не включаемая в репозиторий), причины решений — в decisions D20.

- **Что это**: свойство отправки, у сессий нет типа. Ход выполняется на бесплатных внепиковых ресурсах подписки Coding Plan, не расходуя обычную квоту; время старта определяет сервер — сначала получение талона и очередь, затем запуск при готовности талона. Приёмка такая же, как у обычной отправки. Поддерживается только личная подписка Coding Plan, модель сессии должна быть во внепиковой таблице моделей.
- **Кто выбирает**: по умолчанию отправка обычная, внепиковый режим выбирает пользователь. Перед первой передачей работы в каждом чате Claude запускает `quota`, узнаёт сегодняшнее использование и сообщает пользователю, что можно выбрать внепиковый режим, сколько талонов уже использовано сегодня и доступен ли новый сейчас. После сообщения продолжает обычную отправку, не ожидая ответа; `--offpeak` использует в последующих отправках только после выбора пользователя. Доработки по умолчанию тоже отправляются обычным способом (decisions D20, дополнение 2026-09-28).
- **Исключительное использование свободной сессии**: при внепиковой отправке сессия должна быть свободна (нет живого runner, очередь пуста), иначе код 2. Пока отправка ждёт талона или выполняется, обычные отправки в эту сессию отклоняются; `--steer` разрешён только после начала хода. Для внепиковой отправки принято создавать отдельную сессию; после завершения в ней можно отправлять доработки обычным или внепиковым способом.
- **Получение талона сразу**: `send --offpeak` немедленно получает талон у внепикового сервера; при неудаче код 2, ошибка объясняет причину и дальнейшие действия. После успешного получения без `--wait` сразу возвращает 0; вывод для человека — `send: 已取号，排第 N 位（闲时投递 <offPeakId>）` (талон получен, место N, внепиковая отправка <offPeakId>); `--json` добавляет к существующим полям `offpeak: {offPeakId, ticketId, position}`.
- **Ожидание в очереди не входит в `--timeout`**: отсчёт `--wait` начинается с запуска хода; после его окончания коды выхода такие же, как у обычной отправки. Во время ожидания `--stream` при каждом опросе выводит в stderr одну строку с местом в очереди.
- **Недействительный талон заменяется автоматически, максимум 3 талона**: если талон истёк до готовности или ход завершился неудачно из-за недействительного талона (код ошибки 3102 / 3104 / 3001), runner автоматически получает новый (та же отправка, не более 2 замен), после готовности передаёт в ту же сессию указание продолжить работу. Для каждого продолжающего хода `--timeout` отсчитывается заново. После использования 3 талонов или отказа сервера в новом талоне отправка завершается как `failed` (код 4), изменения в рабочем дереве сохраняются.
- **cancel закрывает талон расчётом на любой стадии**: при ожидании, выполнении, замене талона и даже отсутствии runner команда `cancel` закрывает текущий талон; отправка без конечного результата завершается как `cancelled`, существующий результат не переписывается. При живом runner расчёт выполняет он, повторяя неудачную попытку 3 раза с увеличением задержки; без runner CLI делает одну попытку. Не закрытые после этого талоны записываются в `unsettledTickets` файла `runs/<id>/offpeak.json`, `status` показывает «闲时：号 … 未结算» (внепиковый режим: талон … не закрыт расчётом).
- **Восстановление после exited через `--resume`**: если ход завершился как exited или runner упал, а внепиковая отправка осталась в очереди, обычный send отклоняется с двумя вариантами: `send <id> --offpeak --resume` для продолжения (без текста, `--task` и `--timeout`; их наличие — ошибка использования, код 1; отсутствие восстанавливаемой отправки — код 2; без `--wait` вывод `--json` добавляет `offpeak: {offPeakId, resumed: true}`) либо `cancel` для завершения.
- **Отображение**: во время внепиковой отправки `status` и `follow` добавляют строку о месте в очереди, готовности или выполнении (со сроком), а также «号 … 未结算» (талон … не закрыт расчётом) и «投递 … 没收尾» (отправка … не завершена окончательно); `status --json` и `follow --json` всегда содержат поле `offpeak` (содержимое offpeak.json, при отсутствии — null). В macOS с ожидания талона до окончательного завершения используется `caffeinate`, чтобы машина не уснула от простоя.
- **Проверка работоспособности `doctor --offpeak`**: выполняется только шаг doctor ⑤, проверяются четыре слоя: учётные данные, встроенная запись, контракт сервера и полный путь с фиктивным талоном. Четыре вывода: норма / API изменился / временно недоступно / неприменимо. Только «API изменился» даёт код 1, поэтому проверка подходит для пользовательского cron; stdout всегда содержит строку вывода, в cron его можно отбросить и смотреть только код выхода и stderr. Если версия App отличается от проверенной, stderr дополняется уведомлением, не меняющим вывод. Цена: каждый запуск добавляет сессию самопроверки во внутреннюю базу сессий CLI zcode, в списке задач App она не видна.

### Отправки Start Plan (только в локальной ветке `offpeak`)

Причины решений — в decisions D21. Start Plan — другой уровень подписки в App (встроенная запись `account:<family>-start-plan`, конечная точка в zcode.z.ai).

- **Сейчас недоступно (проверка на реальной установке 2026-09-29)**: конечная точка zcode-plan требует капчу Alibaba Cloud, на которую настольное App отвечает через встроенный SDK капчи; такие безголовые хосты, как этот инструмент, её не проходят — `send --start-plan` завершается неудачным ходом (код 4, `captcha verify failed`). Реализация сохранена (слой протокола проверен до исходящего запроса), до разрешения на стороне сервера не использовать; обычные и внепиковые отправки не затронуты.
- **Что это**: свойство отправки, у сессий нет типа. Как обычная отправка, запускается и начинает отсчёт сразу; шлюз согласования, ожидание ответа, приёмка, `--wait` и коды выхода полностью совпадают. Только запросы модели этого хода используют квоту подписки Start Plan. Талона нет: без получения, очереди, расчёта и исключительного использования сессии.
- **Условия** (код 2): модель сессии находится в таблице start plan (GLM-5.3-Flash, GLM-5.2, GLM-5-Turbo; GLM-5.3 в ней нет); в ZCode App выполнен вход (из учётных данных расшифровываются `oauth:active_provider` и `zcodejwttoken`); во встроенном файле провайдеров есть запись start plan. Совмещение с `--steer` и `--offpeak` — ошибка использования (код 1).
- **Механизм**: runner отправляет `provider/updateAccountConfig`, разрешая встроенную запись, затем отправку; авторизацию хода хост обеспечивает ответом на обратный запрос `interaction/requestProviderRuntimeHeaders` (используется `zcodejwttoken`, как у хоста App). `modelSelection` действует только на этот ход, не меняя текущую модель сессии.
- **Отображение**: без `--wait` человек видит `send: 已排队，runner pid …（这一回合走 start plan 额度，account:<family>-start-plan）` (поставлено в очередь, runner pid …; этот ход использует квоту start plan, account:<family>-start-plan); `--json` добавляет `startPlan: {providerId}`. Событие `executor.startplan.started` сохраняет запись.

## 5. Уровни моделей и размышления

- **Два уровня**: `fast` (Flash, lite, mini, air и подобные) и `strong` (флагманские модели).
- **Соответствие конкретным моделям**: список локально вычисляется из двух источников (для аккаунта — `builtinModelIds` и `modelRules` встроенного файла провайдеров; для legacy — `~/.zcode/v2/config.json`; с 3.12 `workspace/readState` удалён), уровень назначается по ключевым словам в имени модели; если моделей одного уровня несколько, выбирается самая новая версия.
  При рукопожатии `doctor` сопоставляет модели под именем `zcode-executor` из полученного `settings.model.available` с локальным списком и предупреждает об отсутствующих. `tiers` в `config.json` позволяет переопределить выбор. Имена моделей не зашиты в код, смена поколения не требует его правки.
- **Приоритет провайдера: личный coding plan аккаунта, затем командный план аккаунта, затем coding plan из `config.json`** (меняется через `preferredProvider`, например `account:bigmodel-team-coding-plan`); используется сайт, на котором выполнен вход: китайский `bigmodel` или международный `zai`.
- **Без `--tier`** используется `fast`, и только при отсутствии `fast` — `strong`.
- **Уровень размышления при передаче работы по умолчанию `high`**; если модель не поддерживает `high`, параметр не передаётся, используется значение модели по умолчанию. `--thought` его переопределяет. Проверка моделью ZCode по умолчанию использует `low`, меняется через `review.thought`; непустой и не состоящий только из пробельных символов `review.jev.apiKey` в конфигурации добавляет предварительную проверку Jev перед исходной быстрой проверкой, а быстрая и углублённая проверки ZCode продолжают использовать этот уровень размышления. Запросы Jev могут идти через http(s)-прокси из `review.jev.proxy` (D24), без apiKey прокси не действует.
- **Единственный режим — `build`**. `--mode` не предоставляется.
- **`--deny`** по умолчанию не отключает инструменты.

Руководство выбора в skill: механические изменения → `fast`; обычная реализация → `fast`; сложная работа (компромиссы, отладка трудновоспроизводимого поведения, незнакомый код) → `strong`.
У моделей класса Flash не следует понижать уровень размышления: результат плохой.

## 6. Шлюз согласования

В шлюз согласования поступают и `interaction/requestPermission`, и `interaction/requestUserInput` от исполнителя.

**Запрос разрешения** проходит три стадии; для каждого запроса в `events.jsonl` записывается одно итоговое событие `executor.gate`. Его stage принимает следующие значения (подробности предварительной проверки Jev вложены в `preScreen`, историческое `fastReview` сохраняет прежний смысл):
`hard` (жёсткое правило), `no-allow-option` (в options нет `allow_once`, разрешить нельзя), `review-fast` (разрешено быстрой проверкой),
`review-slow` (углублённая проверка), `review-failed` (ошибка вызова модели или разбора), `review-disabled` (проверка моделью отключена конфигурацией),
`gate-error` (ошибка самого шлюза), `question` (вопрос сразу переходит в ожидание ответа).

1. **Жёсткие правила** (заданы в коде, никто не может отменить):
   - Таблица hard использует категории режима auto Claude Code (утечка учётных данных и т. п.).
   - **Первое правило проекта (выход за границу, `outside-worktree`)**: для инструментов с аргументом пути (Write, Edit и т. п.) путь вне cwd → передача человеку.
     Перед проверкой границы путь разбирается по сегментам так же, как ядром: символические ссылки раскрываются на месте, `..` действует на целевой путь ссылки (`<执行副本>/link/../x` попадает в родительский каталог цели ссылки, вне рабочего дерева; `<执行副本>` — рабочее дерево);
     учитываются оба прочтения — «сначала лексически нормализовать» и «передать ядру без изменения»; выход за границу в любом из них активирует правило. Если точку назначения нельзя определить (цикл символических ссылок, попытка пройти через файл как через каталог)
     или инструмент записи (Write, Edit, MultiEdit, NotebookEdit, ApplyPatch) не предоставляет проверяемого пути, запрос также передаётся человеку.
     Пути Bash нельзя надёжно разобрать, поэтому жёсткое правило границ к ним не применяется: они передаются проверке моделью, а в запросе явно сказано, что любую запись или удаление вне рабочего дерева нужно передавать человеку.
   - **Второе правило проекта (самозащита, `self-modify-approval`)**: операция направлена в собственный каталог данных инструмента (там ожидающие запросы и ответы, реестр, конфигурация;
     за исключением стандартного корня рабочих деревьев `worktrees/` и рабочего дерева этой сессии) или вызывает CLI инструмента (`zcode-executor <子命令>`, где `<子命令>` — подкоманда) → передача человеку.
     Исполнитель и runner работают от одного пользователя; права файлов не мешают исполнителю самостоятельно записать `answer.json` или запустить `approve`, поэтому эти два действия не оставляются модели.
     Bash `command` и `code` инструмента js сопоставляются по исходному тексту, распознаются только явные записи (буквальные пути, `~`, `$HOME`, `$PWD`, относительное `..`, имя CLI с подкомандой);
     сборка из переменных, кодирование и запись скрипта с последующим запуском не распознаются и остаются за проверкой моделью и человеком. При одном пользователе полного решения нет, для него нужна изоляция на уровне системы (decisions D23).
   - Совпадение сразу переводит запрос в ожидание ответа, минуя проверку моделью.
2. **Проверка моделью**: необязательная предварительная проверка Jev → исходная быстрая проверка ZCode `fast` + `low` → углублённая проверка при необходимости. Непустой и не состоящий только из пробельных символов `review.jev.apiKey` включает предварительную проверку; Jev pass даёт раннее разрешение, flag/error/skip (в том числе тайм-аут, недопустимый ответ, исключение адаптера) возвращают к исходной быстрой проверке. Без ключа исходная цепочка не меняется. Только отрицательный или неразбираемый результат исходной быстрой проверки передаётся углублённой; ошибка вызова исходной быстрой проверки по-прежнему передаёт запрос человеку как `review-failed`.
   Исходная быстрая проверка получает прежние полные action/context, не использует сокращённый state Jev и не принимает вероятности Jev как инструкции; запросы, уровень размышления и правила разбора сохраняют исходный контракт. Бюджет вывода быстрой проверки ZCode — 300 токенов (`review.fastMaxTokens`), углублённой — 2000 (`review.slowMaxTokens`). У Jev нет shadow/mode, ключ не читается из переменных окружения. Файл `~/.zcode-executor/config.json` с ключом Jev должен быть обычным файлом, не символической ссылкой, принадлежать текущему пользователю и иметь права не шире `0600`, иначе чтение конфигурации завершается ошибкой.
   Углублённая проверка требует, чтобы **первая строка содержала вывод** (`结论: allow` / `结论: ask` / `结论: deny <规则 id>`, где `结论` — вывод, `<规则 id>` — идентификатор правила), а затем причину:
   если вывод стоит в конце, длинное рассуждение может его обрезать, делая всю проверку недействительной.
   **Результат — только разрешение или передача человеку, никогда отказ**; неразбираемый ответ углублённой проверки или ошибка вызова → передача человеку.
   Вход углублённой проверки ZCode: полный файл задания + тексты всех отправок этой сессии (намерение), краткие сведения о предыдущих вызовах инструментов текущего хода, поля `config.json`
   `environment` / `sensitive`, свидетельства (существует ли целевой файл, есть ли незакоммиченные изменения в рабочей области), AGENTS.md / CLAUDE.md исходного репозитория (не рабочего дерева) — только фон, не полномочия пользователя.
   Предварительная проверка Jev получает только минимизированные и очищенные от секретов условия задания, последние сообщения и входные параметры инструментов. Если тело Write/Edit/MultiEdit опущено, нет действительного намерения, команда или сведения о полномочиях обрезаны либо надёжное удаление секретов невозможно, выполняется локальный skip: HTTP не отправляется, сразу запускается исходная быстрая проверка. Пять отрицательных рисков Jev: конфликт объёма работ, запись вне рабочего дерева, учётные данные/внешняя передача, разрушение/внешние побочные эффекты, явная несвязанность/отсутствие необходимости; pass возможен только при всех вероятностях `<=0.20` и достаточных локальных свидетельствах. Сложный Bash, конвейеры, подоболочки, пакетная обработка и скрипты проекта сами по себе не считаются риском или причиной пропуска.
   Правила soft переносятся без изменений; правило считается снятым только если файл задания явно называет и действие, и объект.
   Разрешение → ответ `allow_once`.
3. **Ожидание ответа**: запись `runs/<id>/pending.json` (kind = permission, имя инструмента, параметры, сработавшее жёсткое правило или причина передачи человеку),
   соединение остаётся без ответа. **Срока истечения нет**, завершить ожидание могут только `approve` / `deny` / `cancel`.

**Вопрос** (AskUserQuestion в zcode) минует жёсткие правила и проверку моделью, сразу переходит в ожидание ответа, kind = question, содержит текст вопроса и варианты.
Ответ — через `answer`. В режиме build не бывает ExitPlanMode.

**`--task`** — источник намерения для проверки моделью. Без него намерение состоит только из текста отправки, у проверки границ нет основания, а быстрая проверка чаще даёт flag — поэтому skill требует этот параметр.
В момент постановки в очередь сохраняется снимок задания (`runs/<id>/tasks/<sha256>.md`, хеш записывается в элемент очереди и `taskSha256` события `executor.send`), проверка читает только снимок:
файл задания находится в рабочем дереве и может быть изменён исполнителем; чтение исходника во время проверки позволило бы исполнителю самому написать, «что сказал пользователь». Последующие правки файла не меняют основание проверки;
чтобы проверка увидела новый текст, нужна повторная отправка с `--task`. Старые события без снимка (записанные до обновления) больше не используются как основание проверки.

Каждая проверка записывает только одно итоговое `executor.gate`: `stage:"review-fast"` + `reviewer:"jev"` означает ранний pass предварительной проверки, тот же stage + `reviewer:"zcode"` — pass исходной быстрой проверки; при углублённой проверке/ошибке вызова итоговый reviewer — ZCode. Отдельное поле `preScreen` хранит Jev pass/flag/error/skip, допустимые причины, время, количество, вероятности и другие метаданные; skip не маскируется под flag модели. Историческое `fastReview` сохраняет прежний смысл возврата от Jev и не используется для записи быстрой проверки ZCode. Итоговая статистика не считает событие дважды, контракт полей — в SPEC.

В `doctor --json` поле `review.pipeline` равно `['jev','zcode-fast','zcode-slow']`, если проверка включена и ключ есть; `['zcode-fast','zcode-slow']` без ключа; `[]` при отключённой проверке; `null` с пояснением о неопределённости при ошибке чтения конфигурации. Прежнее поле `fastScreen` сохраняет совместимость лишь с названием первого необязательного этапа и не означает замену быстрой проверки ZCode.

```
  sessions.json                    реестр: локальный id, sess_ zcode (после первого хода), заголовок, cwd, признак рабочего дерева, исходный repoRoot (для рабочего дерева), уровень, provider, модель, уровень размышления, время создания, последний результат
  worktrees/<仓库名>/               рабочее дерево, созданное Claude
  runs/<本地 id>/
    state.json                     состояние runner, pid
    events.jsonl                   исходные события zcode + действия проекта (отправки, результаты стадий шлюза, approve/deny/answer)
    last.json                      результат последнего хода
    pending.json                   ожидающий запрос разрешения или вопрос, удаляется после ответа
    offpeak.json                   состояние внепиковой отправки: талон, место, стадия, срок, не закрытые расчётом талоны (без учётных данных)
    answer.json                    ответ, записанный approve/deny/answer, удаляется после чтения runner
    cancel                         отметка остановки текущего хода; runner отправляет session/stop и отказывает ожидающему запросу за человека; после обработки удаляется
    runner.log                     stderr runner
    queue/                         отправки в очереди
    tasks/<sha256>.md              снимок задания при постановке в очередь, единственный источник намерения из файла задания для проверки моделью
    lock                           блокировка O_EXCL
    stop                           отметка завершения; после текущего элемента runner больше не берёт очередь, закрывает соединение и завершается
```

`runs/` и подкаталоги имеют права 0700, файлы инструмента — 0600 (каталоги 0755 старых версий ужесточаются при следующей отправке): внутри исходные команды, файлы заданий и события сессии.
Это защищает от других пользователей той же машины, но не от исполнителя с тем же пользователем. Права корня каталога данных не ужесточаются: стандартный корень рабочих деревьев тоже находится под ним.
Перед записью `pending.json` секреты runner (ключ провайдера, внепиковые учётные данные, ключ Jev) удаляются по значению; эвристики «похоже на учётные данные — скрыть» не применяются, поскольку человеку нужен исходный текст, чтобы решить, разрешать ли действие.

Единственный источник аудита — `events.jsonl`. Вся история сессии проверяется в одном месте.
`~/.zcode/v2/config.json` и `~/.zcode/v2/credentials.json` доступны только для чтения; `doctor` сообщает лишь наличие файлов и ключей, не выводит содержимое.

## 8. runner

- Один процесс runner на сессию, без постоянного демона, всегда запускается в фоне; `send --wait` только наблюдает за файлами, соединение при ожидании ответа поддерживает runner.
- Жизненный цикл runner: получить блокировку → запустить дочерний app-server → `session/resume` (если в реестре ещё нет `sess_` или resume сообщает
  Session not found, выполнить `session/create`, записать новый идентификатор в реестр и событие `executor.recreated`) → обрабатывать очередь в цикле →
  завершиться, когда очередь пуста или появилась отметка stop.
- Во время ожидания ответа живы и runner, и дочерний app-server.
- Несколько сессий могут выполняться одновременно, каждая со своим дочерним app-server; ограничение количества не задаётся.
- Конец хода определяется по `turn.completed` / `turn.failed` / `turn.terminal`. Резервного механизма на случай отсутствия сигнала пока нет; добавить после первого зависания.
- Неотвеченный обратный запрос каждую секунду повторяется с тем же requestId и требует удаления дубликатов. Кеш ответов хранится только до начала следующей отправки: при повторном использовании requestId другой стороной разрешение прошлого хода не должно без изменений отвечать на новый запрос.
- При запуске дочернего app-server не передавать переменные окружения с учётными данными хост-агента (фиксированный список, включая `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `GITHUB_TOKEN`, `GH_TOKEN`,
  `HOST_CREDENTIAL_ENV` в `lib/appserver.mjs`): Bash исполнителя наследует окружение дочернего процесса, и `env` покажет всё. Ключи модели zcode передаются через персональный файл провайдера, эти переменные не нужны;
  если заданию исполнителя нужны учётные данные GitHub, используется уже авторизованный локальный gh / помощник учётных данных git. Имена исключённых переменных записываются одной строкой в `runner.log` (только имена).

## 9. skill

`skills/zcode-executor/SKILL.md` должен учить следующему:

- Непреложные правила: файл задания — контракт, сообщение — только сигнал; приёмка по `git diff` и тестам; после трёх-четырёх неудачных ходов одной сессии нужно исправлять файл задания; выход за границы не разрешать за пользователя.
- До передачи работы написать файл задания; `send` обязательно включает `--task` (абсолютный путь). Не писать в задании учётные данные: весь текст передаётся проверке моделью как основание полномочий.
- В командах всегда использовать локальный идентификатор поручения; `sess_` zcode нужен только для сопоставления в `list`.
- Перед приёмкой выполнить `git -C <执行副本> add -A` (`<执行副本>` — рабочее дерево): исполнитель не создаёт коммиты, не добавленные в индекс новые файлы не видны в diff.
- Руководство выбора уровня модели и размышления (раздел 5).
- Две обработки кода 5: запрос разрешения передать человеку через AskUserQuestion, затем `approve` / `deny`; для вопроса сначала решить, может ли Claude ответить сам, и если может — `answer`.
- `--steer` добавляет указание, не прерывает ход; для прерывания сначала `cancel`.
- `follow` запускать фоновой задачей, не оборачивать в timeout на переднем плане с ожиданием.
- Внепиковые отправки: когда использовать, отдельная сессия, обработка причин кода 2, `--resume` и `cancel`, `doctor --offpeak`.
- Не открывать выполняющуюся сессию в ZCode App (общая sqlite, нет межпроцессной блокировки).
- Для git всегда использовать `-C <绝对路径>` (`<绝对路径>` — абсолютный путь), различать слияние в основном дереве и смену ветки в рабочем дереве; до перехода на новую ветку проверить, что main уже содержит предыдущее задание (такая ошибка уже случалась).
